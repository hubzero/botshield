Goal

Apache 2.4 module that filters bot and scraper traffic in-process, before Apache hands a request to PHP / FastCGI / upstream. The economic model is: a PHP startup costs ~1 ms × millions of filtered requests = real money. Everything here is in service of "keep cheap filtering cheap and let expensive backends sleep."

Scale target: ~1 M unique IPs / week on one site. Overhead target: sub-millisecond per cookied request; bounded, visible latency on challenged requests.

Primary threat model

Concrete adversaries, not abstract "bots":

  • LLM training crawlers. GPTBot, ClaudeBot, anthropic-ai, CCBot, PerplexityBot, Bytespider, Amazonbot, Applebot-Extended, Meta-ExternalAgent, cohere-ai, Diffbot, ChatGPT-User. They identify themselves (sometimes), ignore robots.txt frequently, and pull full text at huge volume.
  • Distributed scrapers. Rotate through residential IPs (50k+ concurrent), bypassing per-IP rate limits. Often use plain requests / httpx / aiohttp — no JS engine.
  • Headless-browser scrapers. Smaller population, able to solve our PoW, expensive for them per page. We make them pay the cost.
  • Probing scanners. Constant low-volume scans for /.env, /.git/, /wp-admin/, etc. High-signal bait for the scoring engine.

Secondary threats (address with extensions, not core)

  • Slowloris / slow-read — largely handled by mod_reqtimeout. The module's body-read paths (form-captcha verify, M8 captcha-verify, embedded-verify) inherit Apache's Timeout (60 s default); pair with mod_reqtimeout in production for finer slow-client controls. Documented in the operator-facing README under "Slow-client / slowloris defense".
  • Connection hoarding from a single IP — in scope for extensions.
  • Credential stuffing — out of scope; auth layer's job, not ours.

Non-goals

  • Replacing a cloud WAF. Signature matching, L3 DDoS absorption, and global IP-reputation feeds live at the edge.
  • Out-detecting the ML providers. Turnstile / hCaptcha / reCAPTCHA are trained on billions of sessions — we compose them, not compete.
  • Being a rule engine. No DSL, no regex-heavy policy files. That way lies ModSecurity.
  • Being provider-agnostic. Apache first; nginx is a separate project.

Architecture in one paragraph

Two orthogonal axes: challenge tier (what the user experiences: pass / silent JS PoW / form PoW interstitial / full captcha) and verification protocol (how the server trusts that a challenge was actually solved). Requests flow through an early hook that consults a scoring primitive — a simple score_add(penalty, ttl, reason) — and a reputation field read from a single HMAC-signed _bs_verified cookie that doubles as both challenge proof and carrier for accumulated reputation (score + flag bitmap). Per-user state lives in the user's cookie, not in server memory, so a 1 M-IPs-per-week site doesn't blow out SHM. Server state is deliberately sparse: a Bloom filter for "have we seen this IP this week?" and a small flagged-IP table for IPs that tripped something serious (honeypot, scanner probe, fake- Googlebot) — rollback-resistance the cookie alone can't provide. Happy path: users who score 0 never see a challenge and never carry a cookie from us — the module only gates requests whose score crosses a threshold. A successful challenge at any tier re-issues the cookie with preserved rep (minus a tier-dependent forgiveness amount on the score); flags survive forgiveness. Crypto is stateless (HMAC). No per-request network I/O in the hot path except captcha verify at tier 3.

Core milestones

Each milestone is "merge-able" on its own — a visible improvement we can observe in the dev environment before committing to the next. Don't advance until the gate criteria pass.

M0 — skeleton and debug mode

  • Module builds, loads, reads config.
  • BotShieldDebug On in any scope returns 403 "Hello World" to prove the hook fires.

M1 — baseline challenge widget

Went further than originally planned (absorbed what was scoped as a separate form-PoW milestone). A fully-working reCAPTCHA-shaped widget with broad customization — minus the cryptographic integrity that M2 adds.

  • Self-contained HTML interstitial with inline CSS, JS, and Guardian SVG. Zero external asset requests.
  • Asset-extension pass-through.
  • Client-side SHA-256 PoW (N leading hex zeros) with visible progress.
  • Directives: BotShieldEnabled, BotShieldDebug, BotShieldCookieTTL, BotShieldDifficulty, BotShieldPromptText, BotShieldLogoFile, BotShieldLogoLabel, BotShieldHelp (off|on|button), BotShieldHelpFile, BotShieldChallengeFile (full page template with <!-- BOTSHIELD -->), BotShieldShowLogo / ShowLabel / ShowBox.
  • WCAG 2.1 AA verified (axe-core, 0 violations) across default and chrome-stripped variants.
  • Known weakness, resolved in M2: cookie is client-set and server-validated only by regex + timestamp. Forgeable. The baseline still filters every bot that can't execute JS (most of them).

M2 — signed-envelope verification protocol

Replaces M1's client-set pattern-match cookie with an HMAC-signed envelope. Our own protocol — informed by ALTCHA v2's envelope discipline but not bound to its wire format, flow, or KDF vocabulary.

Non-negotiables:

  • Zero extra round trips. The signed challenge is rendered server-side and embedded inline in the interstitial; the cookie is the signed-payload proof.
  • Stateless verify. Every trust anchor in the HMAC-signed envelope.
  • Algorithm-extensible. alg field in the envelope, dispatch registry in code. Ship sha256-zeros; leave slots for SHA-384/ SHA-512/PBKDF2/Argon2 as future opt-ins.

Wire format (every field is covered by the HMAC):

{
  "v": 1,
  "alg": "sha256-zeros",
  "salt": "<hex>",              // 16 random bytes
  "nonce": "<hex>",              // 8 random bytes
  "difficulty": 4,
  "expires_at": 1776900000,
  "signature": "<hex>"           // HMAC-SHA-256 over canonical
                                 // serialization of the rest
}

Cookie = base64(<challenge-json> || "\n" || <counter>) where counter makes SHA-256(salt || nonce || counter) have difficulty leading hex zeros.

Algorithm registry:

static const bs_pow_algorithm bs_algorithms[] = {
    { "sha256-zeros",  1, bs_sha256_zeros_issue, bs_sha256_zeros_verify },
    { "sha384-zeros",  0, NULL, NULL },
    { "sha512-zeros",  0, NULL, NULL },
    { "pbkdf2-sha256", 0, NULL, NULL },
    { "argon2id",      0, NULL, NULL },
    { NULL }
};

After a successful captcha (M8), the cookie's alg is set to captcha-<provider> so scorers can tell how a cookie was earned.

New directives:

  • BotShieldSecretFile /path — HMAC key, mode 600, root-owned.
  • BotShieldAlgorithm sha256-zeros — chooses the issue algorithm; setter rejects unimplemented names at configtest time.

Retirement:

  • bs_has_valid_cookie() (regex + TTL) is deleted. There is no unsigned path post-M2.

Gate:

  • End-to-end PoW flow unchanged for the user; cookie is now signed.
  • Forged cookie → challenged + logged ("signature mismatch").
  • Expired cookie → challenged + logged ("expired").
  • Old-format cookie → challenged (format rejected).
  • BotShieldAlgorithm sha512-zeros → configtest fails with a message naming it as not built into this module.

Risks: libcrypto linkage via apxs; cookie-size (~300 B base64); clock skew handling; secret rotation reserved via optional kid field.

M3 — scoring framework + score-plus-memory primitive

The core abstraction every subsequent feature leans on.

  • Per-request score struct in r->notes, apr_pool-allocated.

  • Cheap built-in heuristics: missing User-Agent, missing Accept-Language, suspicious UA tokens, residential-proxy ASN hints (when GeoIP arrives).

  • First-class primitive:

    void bs_score_add(request_rec *r,
                  int penalty,
                  int ttl_seconds,
                  const char *reason);

    Every penalty source in the module (rate limit exceeded, honeypot hit, scanner probe, failed captcha, fake-Googlebot) calls this. Per-request struct only — penalties die with the request. ttl_seconds is accepted for API stability but ignored; M4's cookie and M5's flagged-IP table are where cross-request state will eventually land.

  • Threshold directives: BotShieldScoreSilent, BotShieldScoreHard, BotShieldScoreCaptcha.

  • Tier decision logs the score breakdown + reason list; still routes everyone to the shipped form-PoW tier. M4.2 makes the tier decision affect routing.

Gate: curl without UA logged high; real browser logged low; reasons appear in the per-request log line.

M4 — single-cookie reputation + happy-path routing

This is where the core design premise crystallizes: per-user state lives in the user's cookie, not in server memory. A 1 M-IPs-per-week site can't afford to allocate SHM per IP; it also doesn't need to. The user carries their reputation as an HMAC-signed blob we handed them.

Split into two sub-commits — the cookie-schema change and the routing-change are separate semantic jumps, and debugging them as one diff would be miserable.

M4.1 — extend the cookie schema, preserve rep across re-issues

The _bs_verified cookie gains rep fields alongside the M2 challenge proof. Extended envelope (every field HMAC-signed):

{
  v                : 1
  alg              : "sha256-zeros"
  salt, nonce,
  difficulty,
  signature, counter,                  // M2 PoW proof
  score            : int, cumulative debt
  flags            : uint32, bitmap of serious-event bits
  passes_silent,
  passes_form,
  passes_captcha   : small counters (operator insight)
  challenged_at    : unix sec — when PoW was solved
  expires_at       : unix sec — hard TTL
}

One TTL, not two. Default BotShieldCookieTTL bumps from 300 s (dev default) to 3600 s (1 h) so real users typically solve PoW once per session. Operator-tunable.

Forgiveness on challenge pass (applied here, in the re-issued cookie):

Tier passed Score −
Silent PoW −10
Form PoW −25
Captcha −50

Floor: max(0, flag_penalty(cookie.flags)) — i.e. numeric score can decay to zero, but a user who tripped a honeypot stays at at-least their flag penalty regardless of how many PoWs they solve. Flags never clear within cookie TTL.

What M4.1 changes vs M3:

  • Cookie parse reads the new fields and exposes rep via a small API (bs_cookie_rep(r) or equivalent).
  • On form-PoW pass, the re-issued cookie applies forgiveness and carries flags, passes_form++, updated challenged_at.
  • Routing is unchanged: everyone below the hard threshold still skips challenging by virtue of having a valid cookie; everyone else still gets form-PoW. M3's effective_score log line now includes cookie_score= and cookie_flags= columns so we can watch the rep accumulate before we start acting on it in M4.2.

New directives:

  • Bump BotShieldCookieTTL default from 300 to 3600.
  • BotShieldCookieDomain ".example.com" — optional; default host- only. Lets rep follow a user across subdomains.
  • BotShieldForgivenessSilent 10, BotShieldForgivenessForm 25, BotShieldForgivenessCaptcha 50 — three separate integer directives (one per tier), each in range 0..10000.

M4.1 gate:

  • End-to-end PoW flow unchanged for the user.
  • After a pass, the cookie contains score = max(0, prior_score − 25) and passes_form = N+1. Inspect via curl + base64 decode.
  • Clients editing any rep field → signature mismatch (inherited M2).
  • Structured log line now emits cookie_score=… and cookie_flags=… on each challenged request, even though routing hasn't changed yet.

M4.1 is shippable on its own: it adds new state to the cookie and lets rep accumulate, without yet taking the risky step of letting cookieless requests pass. If a bug turns up in the rep math, we roll back one commit and M1+M2+M3 are still fine.

M4.2 — happy-path routing: score < silent passes without challenge

This is the visible behavior change. Once M4.1 has demonstrably-correct rep state flowing through cookies in dev traffic, flip the switch on routing:

effective_score = cookie.score + cookie.flag_penalty
                  + request_heuristics
                  + ip_flag_penalty (M5, when present)

if effective_score < BotShieldScoreSilent:
    return DECLINED          // no challenge, no cookie issued
else if effective_score < BotShieldScoreHard:
    serve silent-PoW tier    // stub → form-PoW until M7 ships
else if effective_score < BotShieldScoreCaptcha:
    serve form-PoW tier      // what M1+M2 ship today
else:
    serve captcha tier       // stub → form-PoW until M8 ships

A request that scores 0 gets through without ever seeing a challenge and without ever being issued our cookie — the explicit design goal: legitimate users experience mod_botshield as invisible.

Re-challenge triggers (before expires_at):

  • Score spikes mid-session (new flag set, rate limit breached).
  • User enters a scope with a tighter BotShieldScoreHard.
  • IP lands in the flagged-IP table (M5) between challenges.

M4.2 gate:

  • Fresh browser with realistic headers → score 0 → pass, no cookie ever set. The baseline behavior change from today.
  • curl → heuristic-driven score → challenged.
  • After a PoW pass, subsequent low-score requests pass via rep.
  • Raising score mid-session triggers a re-challenge, and the re- issued cookie carries the new flag.
  • Rollback test: client replays an older lower-score snapshot of their own cookie → passes server-side. This is the documented weakness M4.2 introduces. M5's flagged-IP table is the mitigation.

Retirement of SHM-scoreboard assumptions: the old M4 (per-IP SHM scoreboard for every IP) is gone. Per-IP memory becomes two narrow things only, implemented in M5.

Risk, loudly: M4.2 without M5 is not production-ready against determined scrapers. Replaying an older, lower-score snapshot of their own cookie is exactly the thing a sophisticated actor will try, and M4.2 alone has no defense against it. M4.2 can ship to dev on its own (to see the routing change in action), but M5's flagged-IP table should land close behind before flipping on a real site.

M5 — first-seen Bloom filter + flagged-IP SHM

Sparse server-side state, sized for the working set of active misbehavers — not every IP the site ever sees. Two independent tables backed by the same APR shared-memory segment.

Two sub-commits:

  • M5.1 — flagged-IP table. Closes the M4.2 rollback gap. Brings the base SHM machinery (segment creation, mutex setup, post-config hook, cleanup). Shipped.
  • M5.2 — rotating Bloom filter. First-sight signal, N=2 buffers, rotate-on-insert via CAS, optional mod_watchdog soft-dependency (not wired today — rotate-on-insert is sufficient for correctness). Shipped.

Bloom filter — "have we seen this IP this week?" (M5.2)

Design: rotating (double-buffered) Bloom, N = 2, half-window rotation. Considered and rejected:

  • Single filter with periodic clear. Cliff at reset: everyone is simultaneously "new." Bad.
  • Counting Bloom filter. Solves explicit-delete, not time-based expiry. Wrong tool.
  • Stable Bloom filter. Continuous aging, no boundary, but 2-bit counters (same memory as rotating N=2), more CPU per insert, less widely-implemented, harder to snapshot cleanly. Keep in reserve.

Rotating two-buffer semantics:

  • Both buffers: bit array, m ≈ 9.6 bits/item → ~1.15 MB for 1 M IPs @ 1 % FP, k = 7 hashes.
  • One buffer is active (accepts writes), one is warm (read- only). Queries OR the results of both — an IP counts as "seen" if either buffer has it.
  • Every BotShieldBloomWindow / 2, rotate: active becomes warm, warm gets zeroed and becomes the new active.
  • Per-IP lifetime: between window/2 (if inserted right before a rotation) and window (if inserted right after). Minimum guaranteed memory: 3.5 days for a weekly window — plenty.

k=7 hashes computed via two SipHash outputs + Kirsch-Mitzenmacher double hashing, so the per-insert hash cost is two SipHash-2-4s, not seven.

Concurrency:

  • Insert = k atomic __atomic_or_fetch on uint64 slots. No lock, no CAS.
  • Query = k plain loads. Racing with inserts is benign — Bloom already tolerates probabilistic answers.
  • Rotation = single-writer, coordinated by mod_watchdog (or shutdown-only fallback). An atomic active_index in SHM; workers read it each operation. Brief overlap during swap is tolerable — some writes may land in the "wrong" buffer for a tick, which is just a Bloom union and therefore safe.

Feed / read policy:

  • Feed (insert on first-sight): only when the handler is already about to challenge. Not on every request — skips the ~99% happy- path traffic.
  • Read (first-sight penalty): only on cookieless / sig-mismatch- cookie requests. Cookied-valid users aren't re-penalized for an IP they've already transacted from.

Penalty: small, e.g. bs_score_add(r, 5, bloom_window_secs, "first-sight-ip"). The signal is additive; by itself it never pushes anyone out of the pass tier.

Flagged-IP table — sparse bad-actor set (M5.1)

  • Fixed-size SHM hash table. Default 50 k slots. Keyed by IP (16-byte v6-mapped form). 32-byte slot (cache-line friendly): version (seqlock), flags, 16-byte ip, expires_at.
  • Populated only when a serious event fires — honeypot hit (E3), scanner probe, fake-Googlebot verification failure (E1), repeated PoW-signature failures from the same IP in a short window. M5.1's testable source is the BotShieldFlagIP directive (see below).
  • Read on every request; flags add to effective_score before the tier decision.
  • Entries expire on their own TTL (hours to days, event-dependent).
  • Rollback-resistance: an attacker who replays an older snapshot of their own cookie launders the cookie's contribution but not the IP flag.
  • Hashing: SipHash-2-4 with a key generated at startup (RAND_bytes) and stored in the SHM header. Attackers can't precompute colliding IPs to evict stored entries.
  • Concurrency: lockless reads via a per-slot seqlock (odd = mid-write, even = quiescent); writes take apr_global_mutex briefly and bump the version odd → payload → even. Readers retry a bounded number of times when they catch an odd version or mismatched begin/end versions, then skip the slot.
  • Overflow policy (implemented, simpler than the earlier "shortest-remaining-TTL" text): within a bounded 10-slot linear probe, pick exact-IP match (merge flags, refresh TTL), else first empty slot, else first stale slot, else overwrite the first slot in the probe and log a rate-limited warning. If the table stays saturated under live load, we raise the default capacity rather than get clever with eviction.

BotShieldFlagIP <bit,…> [ttl] is the source operators wire into honeypot or scanner-bait <Location> blocks. It fires on any request hitting the scope — correctness depends on the operator only setting it on paths that a legitimate user would never visit. Built-in bits: honeypot_hit (+60), scanner_probe (+50), fake_bot (+80), pow_fail_streak (+30). E1 (now live) and E3 are the long-term sources; M5.1 ships the integration point now so the table has real traffic during development.

Directives:

  • BotShieldShmSize 8M — total SHM budget (flagged-IP + Bloom).
  • BotShieldFlaggedIPCapacity 50000 — slot count for the table.
  • BotShieldBloomIPs 1000000 — expected working-set size; drives filter dimensions (m, k).
  • BotShieldBloomWindow 604800 — rotation window in seconds (rotation happens every half of this).
  • BotShieldBloomFPRate 0.01 — target false-positive rate at the expected working-set size.

Gate (M5.1):

  • Trigger a flag via a honeypot <Location> → IP shows up in the table; next request from the same IP has the flag's penalty in its effective score and reasons=[flagged-ip:N] in the log.
  • Second honeypot hit merges flags + refreshes TTL without duplicating entries.
  • Config-time caps enforced: BotShieldShmSize 128K..256M, BotShieldFlaggedIPCapacity 1024..1000000, BotShieldFlagIP rejects unknown flag names.
  • Table saturation logs a rate-limited warning (60s) naming the bucket and suggesting a capacity bump.

Gate (M5.2, pending):

  • Unseen IP → "first-sight" penalty appears in reasons list; same IP next request → no penalty.
  • After a rotation, sample a previously-inserted IP just before the half-window boundary and confirm it's still "seen" at least through the second buffer's lifetime.
  • Honeypot-hit path test overlaps with M5.1's existing gate; keep with expected TTL; lookup on next request adds the flag penalty.
  • Fill the flagged-IP table past capacity; confirm eviction picks the shortest-remaining-TTL entry (or clock equivalent), not random.

Thread-safety checkpoint: run under mpm_event. Atomics on read; spinlock only for insert / evict.

M6 — state persistence (Bloom + flagged-IP only)

Narrower than the original plan because cookie-carried rep persists in the user's browser, not in SHM. Only the sparse server-side tables (M5) need to survive restart.

What gets persisted:

  • Bloom filter bit arrays (active + warming buffers).
  • Flagged-IP table entries with remaining TTL.
  • Per-IP verified-bot cache (reserved slot; not in the current E1 implementation, which checks the CIDR files at request time).

Format:

header:
  magic:        'BSHD' (4 bytes)
  version:      uint32 = 1
  saved_at:     uint64 unix millis (little-endian)
  record_count: uint32
records (repeated):
  entry_type:   uint8   (1 = bloom buffer, 2 = flagged IP,
                         3 = reserved for verified-bot cache)
  entry_size:   uint16
  entry_data:   bytes
trailer:
  crc32:        uint32 of all preceding bytes

Extensible: unknown entry_type skipped with a log warning on load.

Lifecycle (as shipped):

  • ap_hook_post_config (parent, after SHM setup) reads the file into SHM, discarding records whose expires_at has passed.
  • apr_pool_cleanup_register on the parent's conf pool writes SHM back to disk on clean shutdown — including graceful reload / restart.
  • Periodic snapshots via mod_watchdog (soft dependency). The callback fires every BotShieldStateSaveInterval seconds (default 300) and re-uses the same bs_state_save path. If mod_watchdog isn't loaded, periodic saves silently degrade to "shutdown-only" with a NOTICE at post-config; the graceful-shutdown save still runs.
  • Atomic durability: write <path>.tmp, apr_file_sync it, apr_file_rename, then fsync the parent directory so the post-rename directory entry is crash-durable.
  • Snapshot concurrency: the flagged-IP table is copied under the global mutex, so a racing writer can't be captured mid-update (version-odd state would otherwise be persisted and look like a freshly-written slot after restore). Bloom buffers are byte arrays mutated by single-byte atomic OR; per-byte reads are torn-free, so they're memcpy-ed without the lock.

Directives (as shipped):

  • BotShieldStateFile /var/lib/botshield/state.bin — default unset (persistence off). Must be at main-server scope, not inside a <VirtualHost> — the SHM segment is module-global.
  • BotShieldStateSaveInterval N — default 300 s. Set to 0 to disable periodic saves (graceful-shutdown save still runs). Range when non-zero: 30..86400.

Gate (M5.1, M6):

  • Snapshot + reload test: populate flagged-IP table, systemctl restart apache2, observe state restored with TTL-respecting decay.
  • Missing state file on startup → empty SHM, log NOTICE.
  • Format-version / magic / checksum / dimension-mismatch all degrade to "start fresh" rather than failing Apache startup.

Risks:

  • Hard-crash loss window. Bounded by BotShieldStateSaveInterval when mod_watchdog is available (default ≤ 5 min). Without mod_watchdog the window is unbounded — the graceful-shutdown save still runs, but a kill -9 loses everything accumulated since the previous clean shutdown.
  • Format evolution. Bumping BS_STATE_FORMAT_VERSION today just discards old files. If we ever need seamless migration, that's a separate pass — not today's problem.

M7 — silent-PoW tier via auto-submit interstitial

The same interstitial we ship today at the form-PoW tier, with the JS wired to fire on DOMContentLoaded instead of waiting for a button click. The user still sees something briefly — a splash page while the PoW runs — but they never click. On success the hidden form auto-POSTs, the cookie lands, and they're redirected to the real URL.

Shape decision (see shapes-considered below):

  • Shape A — auto-submit interstitial. Reuse bs_issue_challenge. Add an auto: true field to the embedded challenge JSON (or a compile-time switch on the tier); the existing inline JS keys off it and starts the Worker immediately. Add a CSS variant that renders the widget as a neutral "checking your browser…" splash instead of the reCAPTCHA-shaped checkbox. No new handler, no output filter, no new code paths for caching / compression / chunked transfer to reason about. ~50 lines of diff.
  • Shape B — output-filter HTML injection (the old M7 design). Rejected. ap_add_output_filter on text/html sounds tidy but the real surface is: interaction with mod_deflate, chunked transfer, mod_cache, Content-Length rewriting, CSP script-src nonces the app already emits, and edge caches in front of Apache. Every one is a cliff we'd have to engineer around. Once Shape C exists for operators who want zero-interstitial integration, Shape B has no constituency.
  • Shape C — embedded silent verification via BotShield wrapper JS. Parked as extension E17. App adds one BotShield <script> tag, BotShield loads the configured provider/native adapter, and verification feeds back into BotShield's own trust state. Bigger lift than Shape A, but still the right opt-in path for operators who can modify templates. Ship Shape A first; Shape C can follow without blocking anything.

What M7 actually changes:

  • New bool field in the challenge envelope: auto — HMAC-covered like every other field. Tier = silent → auto = true.
  • Inline JS in the interstitial checks for auto; if set, kicks off the Worker on DOMContentLoaded instead of waiting for the click handler.
  • New CSS class (or inline-style branch) that swaps the widget chrome for a minimal splash — single centered message, optional small spinner, no checkbox. Reuses the existing a11y scaffolding (landmarks, aria-live status, reduced-motion).
  • Tier routing in the handler: silent_threshold ≤ score < hard_threshold → render the interstitial with auto = true instead of the current stub that falls through to form-PoW.

Gate:

  • Fresh browser scoring into the silent band → sees a brief splash, no interaction, cookie appears, redirect to the real URL.
  • Same client on next request → cookie-valid, DECLINED, no splash.
  • Score into the hard band → existing form-PoW checkbox (unchanged).
  • Score into the pass band → no challenge at all (unchanged).
  • Bot without JS → sits on the splash forever, never gets the cookie. Same end state as form-PoW.
  • WCAG: the splash variant still passes axe-core AA (landmark, aria-live progress, focus order, reduced-motion).

Risks:

  • Perceived latency. The splash is visible. For a difficulty-4 PoW this is a few hundred ms on real browsers; for difficulty-5+ it starts to feel like a loading screen. Default silent-tier difficulty should stay low (3–4); operators who want truly invisible gating move to E17's embedded pattern.
  • Back-button UX. Auto-submit means hitting Back from the real page lands on the splash, which then re-solves and forwards again. Acceptable; mirrors how Cloudflare's "checking browser" page behaves.

Out of scope for M7 (deferred to E17):

  • Serving a separate BotShield wrapper JS at a module URL.
  • An embedded/background verify endpoint under BotShieldEndpointPrefix.
  • App-side <script src=".../embedded.js"> contract.
  • Provider-adapter orchestration and any future native embedded mode.

M8.1 — captcha verify endpoint hardening

The M8 verify endpoint (<prefix>/captcha-verify/<provider>) accepts POSTs and does outbound libcurl to third-party providers. Without guardrails it's a DoS amplifier: one misbehaving client can force thousands of outbound siteverify calls to Cloudflare / Google / hCaptcha / friendlycaptcha / GeeTest, and tie up MPM workers during provider slowdowns. Reviewer-flagged before M9; instrumenting it before observability means M9 counters land with the right things to count already in place.

Reviewer concerns → mitigations:

  • Unbounded outbound amplification. Per-IP rate limit on the verify endpoint backed by a fixed-size SHM counter array (hash- indexed, one-minute rolling window, atomic-CAS updates). Over cap → 429 with Retry-After: 60, no libcurl.
  • Worker starvation during provider slow-downs. Global atomic counter in SHM tracking in-flight siteverify calls; refuse new verifies once the cap is reached. Over cap → 503 WARNING, no libcurl. Counter increments before curl_easy_perform and decrements on any return path.
  • Junk-POST parsing work before network. Cheap prefilters before libcurl is constructed: Content-Type must start with application/x-www-form-urlencoded; total body capped at 8 KB; token field must exist and be within a strict length bound.
  • Random POST spray vs real users. HTTPOnly signed "challenge pending" cookie minted at interstitial render time, checked at verify before libcurl. Missing/expired/tampered → 403, no libcurl. Turns curl -d ... /botshield/captcha-verify/... spray into a guaranteed early reject. Reuses the M2 HMAC secret and primitives.
  • Log flood. Per-IP log-rate-limit for REJECTED/ERROR lines on the verify endpoint: one line per 60 s per IP with a ×N since last suffix. Keeps error.log readable under load without losing count.
  • Intermediate caches. Cache-Control: no-store on all verify- handler responses (currently only on the challenge page).

New directives:

  • BotShieldCaptchaRateLimit N — per-IP verify attempts per minute (default 30, range 1..1000, 0 disables). Scoped per-dir so operators can raise it on scopes that legitimately see more verify traffic.
  • BotShieldCaptchaMaxInFlight N — global concurrent siteverify cap (default 64, range 1..1024). Server-scope only.

New cookie:

  • _bs_captcha_pending — HTTPOnly, 5 min TTL, signed envelope: <nonce_hex>|<expiry_sec>|<hmac_hex> where hmac = HMAC-SHA256(secret, "pending:" || nonce || ":" || expiry). Set at interstitial render, required at verify, cleared (Max-Age=0) on successful verify.

Gate:

  • Flood /botshield/captcha-verify/<p> from one IP with junk tokens → first N succeed or 400/403, subsequent requests return 429 with Retry-After. No libcurl calls after the cap fires.
  • Simulate a slow provider (100 ms timeout against live endpoint), fire verify requests in parallel beyond MaxInFlight → 503 with WARNING on overflow, prior in-flight still complete without corruption.
  • POST directly to verify without pending cookie → 403 "challenge cookie missing" before libcurl.
  • 500 concurrent failed verifies from one IP → log file shows one line per 60 s per IP with ×N since last suffix, not 500 lines.

Risks and accepted trade-offs:

  • NAT false-positives on the per-IP rate limit. Operators behind CGNAT / large corporate NAT may legitimately hit the cap. Mitigation: per-scope tuning, and the pending cookie already absorbs most of the load before the rate limit is the deciding factor.
  • Headless browser bypasses the pending cookie by hitting the interstitial first, then the verify endpoint. Correct — the pending cookie stops blind POST spray, not bot traffic that follows the real UI flow. The libcurl-bound rate limit catches the rest.
  • Direct-to-verify automation (mobile apps, etc.) won't have a pending cookie. Out of scope for the baseline captcha tier; direct API integration is a separate pattern.

M9 — observability

The module had enough moving parts by the end of M8.1 that lack of visibility was the next-biggest risk. M9 surfaces the state already in SHM (M5 flagged-IP table, M5.2 Bloom buffers, M6 save history, M8.1 cv_inflight/cv_rate_slots/cv_log_slots) as machine-readable metrics and structured log lines — no new scoring logic, no new behavior.

Reviewer sequencing discipline: three sub-commits, each with its own gate, so the vocabulary froze before counters were built on top of it, and counters were built before the export surface was built.

M9.1 — structured per-decision log line

One machine-parseable log line per decision, emitted alongside the existing human-readable prose lines (not in place of them). Stable key=value format so the reader doesn't have to parse the prose:

mod_botshield: decision tier=<t> outcome=<o> ip=<i>
    score=<n> cookie=<c> provider=<p|-> alg=<a|->
    reason="<r|->" path="<u>"

Enum values (validated at commit time by a small awk script):

  • tier = none | pass | silent | form | captcha | safeguard
  • outcome = declined | challenged | verified | rejected | failopen | rate_limited | inflight_capped | pending_missing | misconfigured | debug
  • cookie = ok | expired | bad_sig | bad_format | absent | -
  • provider = - or registry name (turnstile/hcaptcha/recaptcha-v2/ recaptcha-v3/friendly/geetest)
  • alg = - or registry entry (sha256-zeros or captcha-)
  • reason = quoted short string or -

Emitted from one central helper bs_decision_log(). Reason and path are double-quoted for logfmt safety; everything else is an unquoted enum so the format parses with a 50-line awk script.

Aligned one naming mismatch along the way: bs_tier_name(BS_TIER_HARD) returned "hard" internally but the plan/log vocabulary used "form". Renamed to "form", which the existing prose log callers picked up naturally.

Gate (shipped): awk validator parses every decision line, confirms every expected key is present, and that tier/outcome/cookie/provider values are drawn from their enum sets. Driven against a 40+ request mix; zero validation failures.

M9.2 — SHM-backed counters

Every decision-log call bumps up to four counters (tier, outcome, cookie when != "-", provider when != "-"). Counter names derive mechanically from the M9.1 enum strings — no parallel vocabulary. Adding a new enum value means adding one row to the string→index lookup; forgetting to do so logs one WARNING and skips the increment rather than silently inventing a bucket.

Counter set (26 total):

  • tier_<t>_total × 5 (one per non-safeguard tier enum; safeguard decisions bin into tier_pass_total since they're functionally pass-through — operators wanting to dashboard the safeguard rate scrape the decision log for reason="challenge- safeguard")
  • outcome_<o>_total × 10 (one per outcome enum)
  • cookie_<c>_total × 5 (one per cookie enum)
  • provider_<p>_total × 6 (one per built-in provider)

Plus persistence metrics (updated in bs_state_save / bs_state_load):

  • Counters: state_saves_total, state_loads_total
  • Gauges: state_save_last_unix, state_save_last_bytes, state_save_last_duration_us, state_load_last_kept, state_load_last_dropped

Plus on-demand gauges (computed when scraped, cached 1s per worker):

  • captcha_inflight_cur (atomic read of the M8.1 semaphore counter)
  • shm_flagged_used / shm_flagged_capacity (table scan)
  • bloom_bits_set_active / bloom_bits_set_warming (popcount)
  • bloom_window_secs, cv_rate_slot_capacity, cv_log_slot_capacity (static from config)

Implementation notes:

  • All counters are apr_uint64_t, incremented with __atomic_fetch_add(..., __ATOMIC_RELAXED) for GCC/clang toolchain consistency with the existing __sync_bool_compare_and_swap used in M8.1 rings. No new linkage.
  • Counter block sits in the same module-global SHM segment as M5/M8.1 state; ~264 bytes added. Children inherit via fork.
  • Counters are not saved to the state file, and do reset across apachectl graceful — the SHM segment is bound to pconf (the config pool), which Apache destroys and recreates on graceful so new config values take effect. Bloom + flagged-IP state survive the graceful round-trip via the state-file save/load dance (runs in the pool-cleanup order, so old SHM → state file → new SHM). Counter reset is a standard Prometheus convention — clients detect it via monotonic-decrease checks. M10.3 verified this behavior on all three MPMs (prefork, worker, event). If we ever want counter persistence across graceful, move apr_shm_create to s->process->pool instead of pconf; that's an M11 packaging- level decision, not an M9 scope item.

Gate (shipped): drive mixed-outcome traffic, assert zero metrics: unknown WARNING lines in the log (= producer/consumer vocabularies are in sync). A stronger value-parity gate runs in M9.3 where the counters are externally readable.

M11 — testing

Until now tests have lived as ad-hoc scripts in /tmp — useful during each milestone, but not reusable. M11 ports them into an in-repo tests/ tree with a shared framework, documented setup, and a single entry point so regressions are caught before they ship rather than after review.

M11 has two phases. Phase 1 (M11.1–M11.3) built a bash-based framework: minimal dependencies (bash + curl + python for the PoW solver), 22 tests green across unit/integration/acceptance, a short- soak smoke for PRs, and a GitHub Actions hook. Phase 2 — pytest + Playwright rebuild

The bash suite works but the seams show. Five structural issues motivated the pivot:

  1. Config mutation isn't transactional. Tests that swap secrets or timeouts (m8_captcha_turnstile, m9_1_enum_coverage, m8_captcha_recaptcha_v2) sed -i the dev vhost, reload, test, revert. A failure between swap and revert leaves the next test running on broken config.
  2. IP allocation is copy-pasted. Every Bloom-fresh or rate-slot-fresh test has its own t=$(date +%s); ip="203.X.$(( ))" block. No coordination across parallel workers.
  3. Log slicing is brittle. Hand-rolled log_mark + log_slice
    • tempfile cleanup per test. grep -q assertions have no diff on failure — "FAIL: expected X" instead of "expected X, found Y, Z".
  4. Captcha-provider tests are five near-identical scripts. Provider differs; assertion shape barely does. Prime candidate for parametrization that bash can't cleanly express.
  5. Acceptance tests fake the browser. form_tier solves PoW in Python and hand-assembles the cookie — it doesn't test what real browsers do (JS worker, auto form submit, redirect status, cookie Path/Domain/Secure attributes honored by a real browser). A real Chromium catches whole classes of bugs the bash suite can't see.

The rebuild uses pytest (mature fixtures, parametrize, markers, xdist) + httpx (HTTP client) + playwright-python + Chromium (real browser for acceptance). Prior art: mod_md's pytest-based suite is the closest pattern in the Apache module ecosystem.

Phase 2 is split into five independently-shippable milestones. Each commits once and leaves the tree green. The bash suite keeps running through M11.4 (parallel CI jobs) and is archived to tests/bash- legacy/ at the start of M11.5.

Extensions

Opt-in features that layer on the core module. Each is one or two milestones' worth of work, independently skippable, and enabled by its own directives. They reuse M3's scoring primitive + M4's SHM + M6's persistence — the cost per extension is small.

E1 — Allow family (verified-bot policy)

Not just UA-string matching — identity verification by CIDR. Implemented; DONE.

  • Built-in entries: Googlebot, Bingbot, Applebot. Ranges come from the provider's published JSON and are cached under /var/lib/botshield/bots/<name>.txt (one CIDR per line). The module reads files at startup; refreshes happen out-of-module via tools/refresh-bot-ranges.sh (cron) so there's no runtime HTTP, no DNS dependency, and a failed refresh just serves stale ranges.
  • Request-time check: UA trie classifier (longest-match wins across all start positions — a specific CorpBot/Admin pattern shadows a generic CorpBot) → CIDR match.
    • In range → bs_score_add(r, -1000, "allow-bot:<name>") — the large negative credit dominates any other signal and puts the request on tier=pass.
    • Out of range → bs_score_add(r, +100, "fake-<name>"). Telling the scorer, loudly, that someone is lying about their identity is valuable signal.
    • No ranges loaded for a matched UA → bot-unverified:<name>, no score delta (benign observation, not a verdict).
  • BotShieldAllowBot <name> <ua-substr> * trusts the UA with no IP check — for internal scrapers where you are the range authority. Emits allow-bot-ua:<name> so operators can filter the weaker-trust variant.
  • Inline CIDRs: BotShieldAllowBot <name> <ua-substr> "198.51.100.0/24,203.0.113.0/24" — accepts a comma-separated list directly, no file round-trip needed.

Config:

BotShieldAllow    on
# Built-ins (googlebot/bingbot/applebot) are auto-registered when
# BotShieldAllow is on. Override the CIDR path, go UA-only, or
# add an entirely new bot via BotShieldAllowBot:
BotShieldAllowBot myscraper  "InternalScraper/"  *
BotShieldAllowBot corpbot    "CorpBot/"  "198.51.100.0/24,203.0.113.0/24"

Metrics: botshield_bot_allow_total, botshield_bot_fake_total, botshield_bot_unverified_total (unlabeled counters).

Deferred: PTR + forward-confirm. The providers that only publish via PTR (Yandex, DuckDuck, Facebook, LinkedIn, Twitter) are lower-value UA-spoofing targets than the CIDR-publishing ones, and adding an async resolver + cache + revalidation state machine is not worth the engineering cost for marginal coverage. Can be added later as a UA-only catchall entry.

E2 — Policy enforcement (rate limiting + path rules + robots.txt)

Feature pin: "Enforces robots.txt." Operator publishes policy once in a file they already maintain; mod_botshield gives it teeth.

The targets are the messy middle of the bot population, not the cleanly-malicious fringe:

  • Many scrapers obey Disallow but ignore Crawl-delay (common in Python/Go crawlers built on parsers that handle path rules but punt on timing).
  • Many obey Crawl-delay per worker while running distributed fleets that don't coordinate — so aggregate RPS is N× the declared rate. Bucketing by UA identity on the server side makes the declared rate actually hold.
  • Some are just badly written: read the file, misimplement the logic, retry-on-429 without backoff. Server-side enforcement catches implementation bugs regardless of intent.

Against the cleanly-malicious population (ignore robots.txt, spoof UAs, rotate IPs), E1's verified-bot CIDRs and per-IP scoring carry the load. E2 is specifically for the population that has declared a policy.

Shared runtime (the load-bearing commitment)

Both E2.1 and E2.2 populate and read the same two in-memory tables. Design these once; source of rules is irrelevant to the matcher.

  • rate_limits: ordered list of (name, cohort, budget, window) → SHM fixed-window counter slot
  • block_paths: ordered list of (name, cohort, path-glob) → 403
  • cohort reuses E1's shape: (ua-substring?, ipspec?). UA match is case-insensitive substring (strcasestr); IP match is apr_ipsubnet_test against the resolved ranges. * on either axis means "any"; both-* is rejected at config time so a typo can't accidentally block or throttle every request.

Precedence for overlapping rules: declaration order, first match wins. Operators order rules most-specific-first. Re-declaring a rule by name replaces the entry in place, preserving surrounding order. Across main/vhost scopes, vhost entries lead in the merged array; main-scope entries act as fallbacks (more-specific scope wins on first-match).

Exceeded rate → 429 + Retry-After and bs_score_add(+50, "rate-limit-exceeded:<name>") so sustained violators feed the score composition, not just the response code. Blocked path → 403 + bs_score_add(+100, "block-path:<name>").

SHM storage: fixed-window counter per cohort (count, window_start pair, atomic CAS on each field — approximate rather than exact sliding window, but correct for rate-limiting semantics operators expect). A flat slot table (BS_E21_RATE_SLOTS = 256) handles hand-written directives and leaves room for E2.2's robots.txt-derived rules; trivial size (~2 KB) next to Bloom + flagged-IP.

Metrics (unlabeled counters, same convention as E1): botshield_rate_limit_exceeded_total, botshield_block_path_hit_total.

E2.1 — Core directives + matcher + SHM bucket

Plain directive-driven policy. Shippable on its own; no robots.txt awareness in the module. Hand-tuned operator policy for the "I looked at my access log and GPTBot is eating 30% of bandwidth, cap it" motion.

BotShieldRateLimit  gptbot    60 min   "GPTBot"     *
BotShieldRateLimit  aws-dc    30 min   *            /etc/botshield/ranges/aws.txt
BotShieldRateLimit  scrapers  10 min   *            "3.0.0.0/8,52.0.0.0/8"
BotShieldBlockPath  gptbot-admin  "/admin/*"   "GPTBot"   *

The last example shows the cohort guard at work: to block /.env we still restrict on UA (a substring pattern that matches common scanner clients) rather than accept both-*. If an operator really wants to block a path from everyone, mod_botshield already supports that via standard Apache mechanisms (<Location> + Require all denied); the Allow-family / policy layer always expresses intent as cohort predicates.

  • Request-time matcher called from bs_handler before bs_run_builtin_heuristics; short-circuits with 403/429 and a decision-log line.

E2.2 — In-module robots.txt parser

src/robots.c parses robots.txt and enforces its rules. The core parser + query API ships in E2.2.1 (landed); live auto-refresh via mod_watchdog is E2.2.2 (next); status surface + fuzz harness are E2.2.3.

BotShieldRobotsTxt /var/www/html/robots.txt

Scope estimate: ~400 LOC including tests. The format is simple (line-based, key: value, # comments, groups bounded by User-agent:), and the subtle parts — path matching with * and $, longest-match-wins between Allow/Disallow, User-agent: * defaulting — are all codified in RFC 9309 plus one de facto extension (Crawl-delay). Google's google/robotstxt is the reference implementation; borrow the test cases for edge behavior, not the C++ code.

E2.2.1 deliverables (shipped):

  • src/robots.c + src/robots.h: defensive parser (length caps, line caps, UTF-8 BOM tolerance) with a public API:
    • robots_parse_file(p, path, &doc, &err) / robots_parse_buf(p, buf, len, &doc, &err)
    • robots_query(doc, ua, path, &match) fills a robots_match struct with group index, wildcard flag, allow/deny decision, and Crawl-delay
    • group-iteration helpers for post_config slot allocation
  • post_config: parse the file per-vhost, populate scfg->robots_doc, assign SHM rate-counter slots from the E2.1 pool to each group that carries a Crawl-delay.
  • Request-time integration in bs_check_policy, layered:
    1. directive block_paths
    2. robots.txt Disallow (wildcard-gated)
    3. directive rate_limits
    4. robots.txt Crawl-delay (wildcard-gated; skipped if a directive rate-limit cohort already matched this request, per the "operator overrides robots.txt" rule).
  • UA matching: per-segment prefix, case-insensitive. The UA header is split on ;; within each segment we strip leading whitespace and (, then the robots.txt token must be a prefix of what remains. Captures the Mozilla-compat idiom (Mozilla/5.0 (compatible; GPTBot/1.0; +https://openai.com/gptbot) — the second segment starts with GPTBot) without the over-matching of a whole-UA strcasestr, which would have let User-agent: Bot fire on any UA mentioning "bot" inside a URL. RFC 9309 strictly says "prefix of UA header" but that misses real crawlers; the segment rule matches Google's reference parser behavior.
  • Duplicate-UA groups are accumulative (RFC 9309 §2.2.1): when the same User-agent token appears in multiple stanzas, the query walks every qualifying group and applies longest-match- wins across the union for Allow/Disallow. Crawl-delay is the max across duplicates (most restrictive; RFC silent on the tie-break). The first qualifying group's name is reported as the reason / slot identifier; duplicate-name groups share an SHM rate-counter slot by construction of the name-keyed map.
  • Path matching: prefix + * wildcard anywhere + $ end-anchor + longest-match-wins between Allow/Disallow (Allow wins ties).
  • Reason strings: robots-block:<group> (403, +100 score) and robots-rate:<group> (429 + Retry-After, +50 score), where <group> is the normalized first-UA of the matching group (e.g. gptbot, wildcard).
  • BotShieldRobotsTxt <path> (TAKE1) + BotShieldRobotsWildcardScope heuristic|strict|off (TAKE1, default heuristic). The wildcard- scope directive gates the User-agent: * group with the crawler- candidate test from the next subsection.
  • Test-staging: /etc/botshield/test-robots/ owned by the test user, group www-data, mode 0775. Needed because Apache's systemd unit has PrivateTmp=true, which gives the apache2 process its own private /tmp namespace — fixtures under /tmp or tmp_path are invisible to the module. Created by tests/setup/provision.sh.

User-agent: * wildcard semantics

This is the load-bearing safety decision of E2.2. A naive literal translation of User-agent: * would apply the rule to any UA — including real users' browsers, which never read robots.txt and have no business being rate-limited or blocked by its rules. A Crawl-delay: 10 under User-agent: * interpreted literally would throttle every visitor to 6 RPM. Pure false-positive territory.

Our interpretation: * means "any crawler not otherwise specified" — not "any UA." We gate *-rule application behind a crawler-candidate test run at request time:

  1. Real-browser-prefix denylist (early out). If UA starts with Mozilla/, Opera/, Firefox/, Edge/, Safari/ AND does not contain bot/crawl/spider/fetch/slurp anywhere → not a crawler candidate, skip * rules entirely. Catches the enormous real-browser population cheaply. Modern headless/bot UAs that embed Mozilla/5.0 typically also include a bot token, so the "and not" clause still reels them in.
  2. Bot-token allowlist. UA contains bot/crawl/spider/ fetch/slurp → crawler candidate. Covers self-declaring bots that weren't registered with a specific BotShieldAllowBot / explicit directive entry.
  3. E1-classifier match. UA already matched a specific cohort via E1's trie → the specific rule applies; * rules are the fallback only when no specific match.

Anything else → do not apply * rules. The test is deliberately conservative on the "hit a real user" axis and willing to miss some crawlers on the * path, because missed crawlers still get caught by per-IP scoring, honeypots, and per-UA explicit directives. A false positive on a real user (rate-limiting Chrome) is a production incident; a false negative on an obscure crawler hitting * rules is a miss we can accept.

Operator escape hatch for operators who want different semantics:

BotShieldRobotsWildcardScope heuristic   # default: the logic above
BotShieldRobotsWildcardScope strict      # apply * to every UA (dangerous — operator's call)
BotShieldRobotsWildcardScope off         # ignore * entirely; explicit UA rules only

Tradeoffs to name upfront:

  • Crawl-delay semantics aren't in RFC 9309; it's a de facto extension. Pick "seconds between requests per cohort" and document it. Common alternatives (requests-per-second, token bucket with burst) are confusing for operators who think in Crawl-delay terms.
  • Format drift risk is low. The format has been stable 25+ years; RFC 9309 codified it in 2022. Google updates the reference parser rarely.
  • License — Google's google/robotstxt is Apache 2.0; borrowing test cases is fine. If any code lifts, preserve their copyright header in that file.

E3 — Path-based triggers (shipped)

Named path patterns that fire on hit. Operator configures what "fire" means: HTTP response, scoring, flagged-IP registration, and an optional log tag that external tools like fail2ban can pattern- match. Framing is "trigger" — neutral about the operator's intent, so the mechanism covers scanner-probe URLs (/.env, /.git/config, /phpmyadmin/ on a non-PMA site), classic honeypots (invisibly- linked bait pages), and anywhere else a request to a specific path should cause a specific reaction.

Not the same thing as E2.1's BotShieldBlockPath — that's cohort- scoped (blocks a specific UA / IP range from a path). Triggers are unscoped: anyone hitting the path causes the action. Both features share the same path-glob matcher (prefix + * + trailing $).

Directive

BotShieldPathTrigger <name> <path-glob> [key=value ...]

Supported keys (all optional; sensible defaults shipped):

status=<code|pass> HTTP response on match. An integer status (e.g. 403, 404, 429, 451) short-circuits the request with that code. The literal token pass means "don't enforce anything on this request" — the request flows through to the real handler, BotShield skips heuristics and interstitials for it, and only the flag-IP + log effects survive to later requests. Default: 403. (No 200 sentinel; 200 is a real status and conflating it with pass-through is confusing for operators reading config.)

redirect= Send a redirect response to the given URL. Implies status=302 when status isn't set explicitly; operator can pair with status=301 / status=307 / status=308 to pick semantics. Mutually exclusive with status=pass (a redirect IS the response). URL can be absolute or site-relative; emitted as the Location: header.

log= Optional tag string embedded in the request's decision-log line as tag="<string>". No second log line; the tag lives in the existing per-request decision log so external tools have one stable thing to grep. Example use: log="BAN 2h" with a fail2ban filter that pattern-matches the tag to drop the IP into a 2-hour ban jail.

flag= M5.1 flagged-IP bit to set for future requests from this client. One of the module's registered names: scanner_probe (+50 on future requests), honeypot_hit (+60), fake_bot (+80), pow_fail_streak (+30). Default scanner_probe. The bit's magnitude is fixed by the flag registry; operators pick the bit to pick the magnitude. Unknown names are rejected at config time.

ttl= Flagged-IP TTL in seconds. Default 3600. 0 means "don't flag" (trigger acts on this request only, no persistent memory).

penalty= Additional bs_score_add amount applied under status=<code> only — shows up on the decision log for this request, but since an error status is already being returned the penalty is bookkeeping, not a tier decision. Ignored under status=pass (pass-through requests are not scored by the trigger; the flag-IP bit carries the later-request effect instead). Default 0. Use it when the flag bit's built- in magnitude isn't enough and you want the decision log to carry a larger in-request penalty number too.

Precedence on overlapping patterns

Directives match in declaration order, first match wins. So if an operator writes

BotShieldPathTrigger wp-ajax "/wp-admin/admin-ajax.php" status=pass penalty=0
BotShieldPathTrigger wp-all  "/wp-admin*"               status=403

the more-specific wp-ajax rule fires on /wp-admin/admin-ajax.php (pass-through) while /wp-admin/anything- else matches wp-all (403). Operators put specific-before- generic to get the natural shadowing behavior, same idiom as E2.1 BotShieldBlockPath.

Re-declaring the same <name> replaces the existing entry in place — upsert-by-name — so a later directive can override a trigger without reshuffling surrounding rule order. Main-scope triggers merge into vhosts the way E2.1 rules do (vhost entries lead, main entries append as fallbacks).

Examples (these are docs, not shipped built-ins)

# Classic scanner probe — immediate 403, tag the IP for fail2ban,
# and flag the IP with scanner_probe (+50 on future requests for
# a day). `flag=` defaults to scanner_probe so the key is left
# off in this example.
BotShieldPathTrigger env-probe     "/.env"                 \
    status=403 log="BAN 2h" ttl=86400

# Honeypot page invisibly linked from the footer. Let the app
# serve whatever it'd normally serve (status=pass), but flag the
# IP with honeypot_hit (+60 on every subsequent request for a
# day). Scoring effect lands on LATER requests, not this one.
BotShieldPathTrigger honeypot-1    "/contact-archive.html" \
    status=pass flag=honeypot_hit ttl=86400

# Redirect the scanner somewhere informative (or to a separate
# trap host you run). 301 is permanent; scanners that cache
# redirects will never come back.
BotShieldPathTrigger env-redirect  "/.env"                 \
    redirect="https://example.org/no-secrets-here" status=301

# Silent scanner detector on a non-WordPress site — pass through
# to the real handler (which will 404 naturally), but flag the
# IP so later requests carry the scanner-probe score bump.
BotShieldPathTrigger wp-probe      "/wp-admin*"            \
    status=pass ttl=3600

# Credential-file probe. Big penalty on this request's decision
# log (for analysts reading the log), plus a day-long flag.
BotShieldPathTrigger creds-probe   "/.aws/credentials"     \
    status=403 log="BAN 24h" penalty=200 ttl=86400

No curated built-in list. Ship zero triggers by default; operators declare what they want. A list of "things you probably want" lives in the docs, not in compiled code — so the module never silently widens enforcement when the list changes version to version.

Apache ErrorDocument compatibility

A trigger whose action is an error status (status=403, 404, 429, 451, etc.) returns that status code from the handler without writing any body. That's the shape Apache requires to run its ErrorDocument machinery — operators' existing ErrorDocument 403 / 404 / 429 directives fire normally, and in their absence Apache's built-in default error pages render. Two implementation rules the code must honor:

  • Do not write a response body on error-status triggers. The request path sets up headers (Retry-After for 429, etc.) and returns the status code; Apache handles the body.
  • Do not set r->status + return OK as a shortcut — that pattern tells Apache "I already produced the response," which suppresses ErrorDocument. Return the status code directly.

status=pass returns DECLINED so the real handler runs — also intentional, and the request's final status comes from whatever downstream produces.

redirect=<url> sets Location: and returns the redirect status (302 by default). ErrorDocument doesn't apply to redirects in Apache (they're not errors); the browser follows the redirect and the target page is whatever the operator pointed at.

Decision-log integration

When a trigger with log= fires, the existing request decision-log line carries an extra tag="<string>" field. No second emission — external tools watch one stable pattern per request.

mod_botshield: decision tier=pass outcome=rejected ip=1.2.3.4 \
    score=50 cookie=absent provider=- alg=- \
    reason="[trigger:env-probe:50]" path="/.env" tag="BAN 2h"

For triggers without log=, no tag= field is emitted; the decision log looks identical to any other rejected-request line.

E4 — Cookie triggers (shipped)

Counterpart to E3 path triggers. Named rules that fire when a cookie on the request matches the operator's predicate. Same key=value action surface as E3, plus a credit=<n> key for negative-score contributions — the mechanism for "the app's session/auth cookie tells us this client is trusted; glide them through tier dispatch."

Two shapes operators use this for:

  • Positive signals. App's session cookie (PHPSESSID, etc.) or auth cookie says this client is a real visitor the app already opened a session for. Fire a credit=<n> so heuristics can't easily push them into a captcha tier.
  • Negative signals. A cookie with a known-bad value (leaked- credential list, honeypot-bait value we minted into the HTML) is a replay attempt or a malicious scan. Fire status=<code> + flag=<bit> + log=<tag> the way E3 does for bad paths.

Both live under one directive because the matching is identical; only the operator's intent differs.

Directive

BotShieldCookieTrigger <name> <cookie-match> [key=value ...]

<cookie-match> shapes (exactly one required):

Per-named-cookie predicates: cookie= Cookie is present (any value). cookie== Cookie has exactly this value. cookie=~ Cookie value contains substring. cookie=! Cookie is present but value is NOT the given one. !cookie= Cookie is absent from the request.

Bulk-state predicates: cookies=none Request carries no cookies at all (bots that don't accept cookies). cookies=any Request carries at least one cookie (complement of cookies=none). cookies=session Request carries at least one cookie whose name is on the module's known- session-cookie list. Curated default: PHPSESSID, JSESSIONID, ASP.NET_SessionId, session_id, connect.sid, laravel_session. Operators extend via the BotShieldSessionCookieName <name> directive — same scope rules as other server-config directives.

BotShield's own cookie (computed during the normal cookie- verification pass earlier in bs_handler, exposed here so operators can layer on top of the result without parsing _bs_verified themselves): bs-cookie=verified Valid _bs_verified cookie present and passed HMAC + freshness checks. bs-cookie=missing No _bs_verified cookie on the request. bs-cookie=invalid _bs_verified present but HMAC or format verification failed (e.g. tampered, expired, cross-secret).

Cookie-name validation (per-named predicates): <cname> must match [A-Za-z0-9_-]{1,64}. Operators declaring a trigger against the module's raw _bs_verified cookie name are redirected with a config-time error to use bs-cookie=<state> instead — that channel exposes the verification verdict, not the raw bytes.

Action keys (all optional):

credit=<n> Subtract N from this request's score. Range 0..1000. Typical values: 15 (session), 40 (auth), 100 (signed claim — see "future layer" below). Use for positive-signal triggers. penalty=<n> Add N to this request's score. Same range. Use for suspicious-cookie triggers. status=<code|pass> HTTP response on match. Default pass. Unlike E3, pass here still applies credit/penalty to THIS request — cookie presence is a persistent signal the client carries with them, so shaping this request's score is the whole point. Set status=<code> when a bad cookie should short-circuit (e.g. 403 on a known-stolen token). redirect=<url> Redirect response. Implies 302 unless status=3xx is explicit. Mutually exclusive with status=pass — same rule as E3. flag=<bit> M5.1 flag-IP bit. Same registry as E3 (scanner_probe, honeypot_hit, fake_bot, pow_fail_streak). ttl=<sec> Flagged-IP TTL. 0 = don't flag. log=<tag> Decision-log tag= field — same as E3, rides the existing decision line.

Semantics differences from E3 (READ THIS — the status=pass meaning is not the same)

Two points where Cookie triggers diverge from Path triggers on purpose, because cookies are ongoing-state signals and paths are one-off events. The difference is easy to forget — document it loudly in the setter's doc comment, in the directive's help text, and in the tests so future readers (including future us) don't assume E3's rules carry over.

  1. credit=/penalty= always apply, regardless of status=. A cookie trigger's whole point under status=pass is to shape this request's score — the client is CARRYING the signal on this very request, via the cookie they sent. (Contrast E3 path triggers: status=pass there means "no enforcement on this request; only flag-IP as future memory." For path triggers penalty is ignored under pass. For cookie triggers it is not.) A cookie trigger's flag=<bit> + ttl=<sec> still work for future-request memory on top of the current-request score effect.

    The tests MUST assert both sides explicitly: "cookie trigger under status=pass reduces this request's score" AND "path trigger under status=pass does not change this request's score."

  2. Cookie triggers run BEFORE path triggers inside bs_check_policy. Rationale: reputation signals from cookies should shape the score record first so the decision log tells the complete story, including for cases where a later rule short-circuits. Either family can short-circuit; first match in family-declaration order wins.

v1 non-goals (pin these so scope doesn't creep)

  • No regular expressions. The predicates are deliberately boring: presence, absence, exact-value, substring. If operators need regex matching, they write it in their app handler and send feedback via E5. Adding regex here means shipping PCRE into the hot path, handling malformed patterns at config time, and opening a CVE surface we don't need.
  • No generic expression language. No boolean AND/OR between predicates, no comparison operators on numeric cookie values, no "match cookie X if cookie Y also present." Operators layer two separate triggers and let their credit/penalty values sum.
  • No cookie-attribute matching. The module only inspects the client-sent name=value pairs. It doesn't (and can't) see the browser's original Domain/Path/Secure/ HttpOnly attributes — those are set by the issuer, not transmitted back. Anyone asking for domain=example.com is asking for something the Cookie header doesn't carry.
  • No multi-value cookies. Browsers shouldn't send the same cookie name twice; if they do, we use the first occurrence and ignore the rest. No RFC 6265 edge cases.

Keeping v1 boring lets us wire up the common 90% cleanly. If pressure builds for any of the above later, each one is an additive feature that lands without breaking the current surface — better than reverse-engineering complexity out of a general expression language later.

Guidance: keep credits small

Cookie presence is a hint, not proof of legitimacy. An attacker who successfully logs into the app (or steals an auth cookie) gets the credit too; anything you credit generously becomes a speed-up for post-compromise behavior. Recommended ballpark:

  • cookies=any / cookies=session — single-digit credit (5).
  • Named session cookie (cookie=PHPSESSID) — ≤ 20.
  • Named auth cookie (cookie=auth_token) — ≤ 40.
  • Signed HMAC claim (future layer) — up to 100.

The cookies=session built-in name list is deliberately short: PHPSESSID, JSESSIONID, ASP.NET_SessionId, session_id, connect.sid, laravel_session. Each matches a framework default. Operators running other stacks extend via BotShieldSessionCookieName. A long auto-list would turn the predicate into a loose any-cookie-with-a-suggestive-name matcher and undermine the bonus.

Similarly, app-specific assumptions like "admin cookie on non-admin path is suspicious" are only true for some apps — the docs should show them as templates operators adapt, not as built-in rules we ship enabled.

Precedence within the family

Declaration order, with a deliberately split rule that makes the layered-reputation use case (multiple session/auth credits on the same client) actually work:

  • Pass triggers accumulate. Every cookie trigger with status=pass that matches applies its credit/penalty to the request's score and its flag+ttl to the IP, then the evaluator keeps scanning. That's how the canonical "app-session credit=15 + app-auth credit=40" example produces a 55-point credit when both cookies are present — rather than losing the second credit to first-match-wins.
  • Non-pass triggers short-circuit. The first trigger that matches with status=<code> / redirect= returns that response immediately, ending the walk. Any pass-trigger credits/penalties that already accumulated during the walk are preserved in the decision-log score field; they're moot for the response (the status is what the client sees) but recorded for analysts.
  • Upsert-by-name at config time still holds: re-declaring a trigger with the same name replaces the prior entry in place rather than creating a duplicate.
  • Main → vhost merge reuses bs_merge_rule_array (same as E2.1, E3). Vhost entries lead, main-scope entries append as fallbacks.

This is the one meaningful divergence from how E3 path triggers handle precedence (there it's strict first-match-wins with no accumulation), and it exists for the same reason the credit/penalty-under-pass divergence exists: cookies are ongoing- state signals that naturally compose, not mutually-exclusive path matches.

Examples

# Layer 1 — named app session cookie present → 15 off
BotShieldCookieTrigger app-session   cookie=PHPSESSID  credit=15

# Layer 2 — named auth cookie present → 40 off
BotShieldCookieTrigger app-auth      cookie=auth_token credit=40

# Framework-agnostic session bonus. Fires on any cookie name
# in the known-session list, so operators who don't want to
# commit to a specific cookie name get a small credit anyway.
# Use INSTEAD of the two above when the site runs a mixed stack.
BotShieldCookieTrigger any-session   cookies=session    credit=10

# Cookie-less clients get a small bump. Real browsers carry
# cookies by the second pageview; naive scrapers never do.
BotShieldCookieTrigger no-cookies    cookies=none       penalty=5

# Client cleared a BotShield challenge already → extra credit
# on top of whatever the module internally gives the cookie.
# Useful when heuristic signals would otherwise push a
# verified client into captcha tier.
BotShieldCookieTrigger bs-verified   bs-cookie=verified credit=30

# Client sent a _bs_verified cookie that failed HMAC.
# Attempted replay or tamper. Flag the IP.
BotShieldCookieTrigger bs-tampered   bs-cookie=invalid  \
    penalty=80 flag=honeypot_hit "log=BAN 1h" ttl=3600

# Known-bad cookie (value from a leaked credential list).
# Block immediately + flag the IP for a day.
BotShieldCookieTrigger stale-token  cookie=api_token=LEAKED_HEX \
    status=403 flag=honeypot_hit "log=BAN 1d" ttl=86400

# Admin cookie from a client hitting non-admin paths —
# suspicious. Penalty without block; operator's other
# heuristics decide the final tier.
BotShieldCookieTrigger lurking-admin cookie=admin_session \
    penalty=50 flag=scanner_probe ttl=3600

# Substring match on a honeypot cookie we injected into the
# signup-failure page. Its presence means a bot replayed a
# stale form. Status=pass so the request still reaches the
# app (which will 200 an inert response), but the penalty
# flips positive — we KNOW this is a scraper.
BotShieldCookieTrigger honeypot-signup \
    cookie=signup_tmp~BAIT-HEX penalty=80 \
    flag=honeypot_hit ttl=3600

# Logged-in user missing our CSRF cookie → their form will
# fail at the app anyway, but flag the attempt so repeat

BotShieldCookieTrigger missing-csrf  !cookie=csrf_token \
    penalty=20 flag=scanner_probe ttl=600

Cookie parsing — parse once, reuse

Implementation rule: tokenize the Cookie header exactly once per request, into a pool-allocated apr_table_t (or apr_hash_t) of name → value, and have every cookie trigger consult that map. Do not re-scan the raw header per trigger.

On a page with N cookie triggers and M cookies on the request, the obvious-but-wrong implementation is O(N × M) string scans across the raw header — a small amount of work per trigger multiplied by however many operators layer. Parsing once is O(M), after which each trigger is an O(1) hash lookup plus the predicate's value comparison.

The parse itself:

  • split on ;
  • trim ASCII whitespace
  • first = separates name from value (values may contain =)
  • cookies without a value (Cookie: foo) are treated as present-with-empty-string: match cookie=foo and cookie=foo= but not cookie=foo=anything
  • duplicate-name cookies: use the first occurrence, ignore the rest (browsers shouldn't emit them; if they do, we don't want to guess which one is the "real" one)

The parsed map lives in r->pool so it dies naturally with the request. The bs_check_policy E4 walk fetches (or lazily builds) it once and passes the pointer down to each predicate check.

The _bs_verified cookie's verification verdict is already computed earlier in bs_handler and stored in a per-request variable (cookie_verify_reason) — the bs-cookie=<state> predicate reuses that verdict directly; it does not re-verify.

Future layer: HMAC-signed claims

The original E4 design reserved a Layer-3 shape where the app issues a signed claim cookie and the module verifies the HMAC:

BotShieldCookieTrigger app-auth-signed \
    cookie=bs_auth_claim \
    hmac=/etc/botshield/app-auth.key \
    credit=100

The module would parse the cookie value as <expiry>;<sig>, verify the signature, check the expiry, and apply the credit only if valid. Not part of v1 — the plain-value matching above covers the cooperative-app case; add HMAC once operators actually want adversarial resistance on the cookie path.

Tradeoffs

  • A compromised cookie value leaks the credit. Plain-match is cooperative-app only; if the cookie is interesting enough to steal, use the future HMAC layer (or pair with E5 app-to- module feedback for out-of-band signalling).
  • Cookie triggers don't distinguish guest-session from auth- session inherently — operators declare two separate triggers for PHPSESSID (Layer 1) and auth_token (Layer 2) and let the credits sum naturally.
  • No support for removing flags via a cookie signal. Flag removal is harder to reason about than flag-adding; keep it one-way for v1 (E5 already defers the same question for the app-to-module channel).

E5 — App-to-module reputation feedback (shipped)

The mirror image of E4. E4 lets the app's state (logged-in session, auth cookie) shape a client's score; E5 lets the app push the score in either direction when it catches something mod_botshield can't see from request-level signals alone — failed-login streak, spammy form post, abusive API usage, business-rule violation. The app can't see SHM directly, so it needs a channel.

Shape — response header, stripped before send:

  • App sets a header on its response, e.g.:

    X-BotShield-Feedback: flag=pow_fail_streak;ttl=3600;sig=<hex>

  • Module reads the header in a response-phase hook that runs before the response leaves Apache (a fixups-style handler on r->headers_out, or an output filter positioned before the protocol layer — not log_transaction, which fires after headers are already on the wire). The hook validates the HMAC signature against a shared-secret key, parses the flag + TTL, strips the header from r->headers_out, and either calls bs_flagged_ip_add directly or stashes the parsed result in r->notes for a paired log_transaction handler to write to SHM. The split is an implementation detail; what's not optional is that stripping happens before the response goes out so clients never see the header.

  • Same flag-bit registry the BotShieldFlagIP directive already uses — plus three credit-carrying bits added for E5's bidirectional use case. Penalty bits: honeypot_hit (+60), scanner_probe (+50), fake_bot (+80), pow_fail_streak (+30). Credit bits: app_verified_human (-80, strongest — app completed a high- friction verification like MFA or admin approval), app_verified_session (-40, authenticated session the app trusts), app_trust_signal (-20, smaller positive for a quietly-good signal). Penalties and credits compose additively in bs_flag_penalty — if an IP trips a honeypot on Monday (+60) and the app verifies the human on Tuesday (-80), that IP's future requests carry a -20 flag contribution until the shorter-TTL bit expires. That's the right semantic: the app's later judgment balances the earlier observation rather than erasing it. App operators still don't get to invent new flags without a matching code addition — keeps the scoring surface small and auditable.

  • IP is r->useragent_ip by default (the module's normal keying, respecting mod_remoteip). Operators of multi-site app clusters who route through intermediate workers may need ip=<addr> in the header; deferred until there's a real use case.

Why a header and not a POST endpoint:

  • Synchronous with the request that produced the signal — no new round-trip, no new auth surface.
  • Works from any backend language that can set a response header (PHP, Python, Node, Go).
  • Stays within the same Apache request, so r->useragent_ip is already unwrapped by mod_remoteip — the app doesn't need to know the real client IP.
  • Apache's response-phase hooks fire before the headers hit the wire — the module can read, validate, and strip the feedback header in one pass, then write the flag to SHM in time for the next request from the same IP to see it.

Why HMAC and not a static secret:

  • Header channel is server-to-server in principle, but an app bug (reflected header, header-injection vuln) could let a client plant it. A static bearer secret in the header value survives one Header directive + one log-line leak away from disaster. HMAC-SHA-256 over the content, keyed by a file-backed secret, mirrors the M2 pattern the module already ships.

Wire format (fields separated by ;, HMAC covers everything up to but not including the ;sig= suffix):

flag=<name>;ttl=<seconds>[;kid=<id>];sig=<hex>

Directives:

  • BotShieldAppFeedback on|off — default off; opt-in per scope.
  • BotShieldAppFeedbackHeader X-BotShield-Feedback — header name, in case an operator needs to avoid a collision.
  • BotShieldAppIntegrationSecretFile /etc/botshield/app-integration.key — shared HMAC key for both app→module feedback envelopes and module→app X-Botshield-Claims headers. Mode 600, root-owned. Separate from the challenge secret so compromise of one doesn't cross-contaminate. Cross-replay between feedback and claims is blocked by the protocols' structurally-distinct canonical forms (parser-level domain separation), not by key separation.

Composition with existing scoring:

  • Feedback fires bs_flagged_ip_add with the configured TTL; the per-flag penalty comes from bs_flag_penalty the same as honeypot/scanner paths. No new scoring primitive — just a new source of flags.
  • Because flags live in SHM (not the cookie), cookie rollback doesn't launder them. Persists across restart via M6 state file.

Implementation rules (pin these before coding)

The shape above leaves a few decisions to make during implementation; pinning them up front keeps the review surface small later.

  1. Strip the header in a response-phase hook, not log_transaction. log_transaction fires after headers are already on the wire — too late. Read + strip belong together in one fixups-style / output-filter handler that runs before the protocol-layer flush. The SHM write can stay in that same handler or be deferred to log_transaction via r->notes; the stripping cannot.

  2. Strip the header unconditionally when present, even with BotShieldAppFeedback off. An app that emits the header during a configuration mistake (feature accidentally off, or operator-staged config rollout) should never leak it to the client. One apr_table_unset is cheap; the safety is absolute. The feature-off optimization is "don't parse or validate when off" — it's NOT "don't touch the table."

  3. Duplicate headers: reject and strip both. If the app emits X-BotShield-Feedback more than once, reject the feedback (no flag applied, log at APLOG_INFO) and strip every instance. Refusing to guess which copy is authoritative prevents an app-bug + header-injection combo from letting a client plant the second header. apr_table_getm / iterate accordingly.

  4. Skip subrequests. Gate on ap_is_initial_req(r) so synthetic subrequests (mod_include, ap_sub_req_lookup_*, mod_autoindex fetches, etc.) are no-ops — their r->headers_out is merged or discarded by the parent and shouldn't independently flag an IP. Note that ap_is_initial_req distinguishes main requests from subrequests; it does NOT distinguish the original request from an internal redirect (ErrorDocument fetch, RewriteRule internal redirect, etc.), because those are new main requests that replace the current r. That's the right behavior here: if an internal-redirect target's response carries the feedback header, we DO want to strip it and apply it — it's a fresh main request that came through the full pipeline and mod_headers' directives fired on its own scope. Applying twice (once per leg of an internal redirect) is the correct semantic, not a bug; operators who don't want that scope their Header directive appropriately.

  5. Strip on the error-response chain too. Apache builds a separate output filter chain via ap_die for 4xx/5xx responses (missing-file 404s, handler-returned errors, ErrorDocument redirects). The normal-chain ap_hook_insert_ filter doesn't fire there. Register the same filter via ap_hook_insert_error_filter in addition to the normal hook so the "header never visible to client" promise holds on error responses too. The filter is idempotent and one-shot, so double-registration is safe.

Gate:

  • App sets a valid signed header → client's IP appears in the flagged-IP table with the requested flag + TTL; next request from that IP includes the flag's penalty in effective_score and reasons=[flagged-ip:N] in the log line.
  • Tampered signature → rejected + logged at APLOG_INFO; no flag applied; header still stripped.
  • Unknown flag name → rejected + logged; no flag applied.
  • TTL clamped to a sane range (e.g. 60 s .. 30 d); request outside the range is rejected.
  • Duplicate X-BotShield-Feedback headers → rejected + all instances stripped.
  • Subrequests → handler is a no-op.
  • Header never visible to the client on normal responses — curl the app and confirm the X-BotShield-Feedback header is absent from the response.
  • Header never visible on error responses either (404 for a missing file, ErrorDocument redirects, handler-returned 4xx/5xx) — same curl check on an error path must return a clean response.
  • BotShieldAppFeedback off (default) → parse/validate path skipped; stripping still runs so a misconfigured app can't leak the header to clients.

Risks:

  • Key rotation. Reserve kid=<id> for multi-key verify; follow the same pattern the M2 envelope leaves open for the challenge secret.
  • Reflected-header style app bugs. If an app accidentally echoes a user-controlled header into X-BotShield-Feedback, the HMAC check fails and the penalty is discarded. The flag-name whitelist plus TTL clamp bound the blast radius if the key does leak.
  • Deployment coupling. Shared secret means the app and Apache need coordinated secret distribution. Standard secrets-management problem; not unique to this feature.

Example: form-field honeypot feedback

Form-field honeypots (hidden inputs that real users can't fill but naive bots autofill) are a natural fit for this channel — the app already parses the form body, already knows the schema, and already knows which fields were filled. Module-side form inspection would require body buffering, content-type handling (urlencoded + multipart + JSON), and a per-form-per-fieldname config surface that duplicates what the app already has. Instead, the app detects the honeypot fill and sends the feedback header.

PHP sketch:

if (!empty($_POST['website'] ?? '')) {   // hidden honeypot field
    $ttl  = 3600;
    $flag = 'honeypot_hit';
    $body = "flag=$flag;ttl=$ttl";
    $sig  = hash_hmac('sha256', $body,
                      file_get_contents('/etc/botshield/app-feedback.key'));
    header("X-BotShield-Feedback: $body;sig=$sig");
    // still 200 — don't tell the bot it was detected
}

Same pattern works for any app-detected signal: failed-login streaks, abusive API usage, business-rule violations. The module stays agnostic about what the app considers bad; it just applies the signed flag.

Example: BotShield-cookie-stripping detection

The app is the only observer with both signals available: (1) "is this client authenticated to the app?" and (2) "is the _bs_verified cookie absent on the request?" If both are true — the user is logged in but BotShield's own cookie is gone — something stripped or cleared the cookie deliberately. Real browsers don't do that; scrapers that replay captured auth cookies while wiping other trackers do.

The module can't detect this on its own because it doesn't know the app's auth state. The app feeds it back:

$logged_in   = /* app's own auth check */;
$has_bs_ck   = !empty($_COOKIE['_bs_verified'] ?? '');
if ($logged_in && !$has_bs_ck) {
    $ttl  = 86400;
    $flag = 'fake_bot';   // +80 on future requests
    $body = "flag=$flag;ttl=$ttl";
    $sig  = hash_hmac('sha256', $body,
                      file_get_contents('/etc/botshield/app-feedback.key'));
    header("X-BotShield-Feedback: $body;sig=$sig");
    // still 200 — serve the response the user asked for;
    // the flag costs them on their NEXT request.
}

Pairs naturally with an E4 bs-cookie=missing cookie trigger for the anonymous case. E4 catches clients who visit without a BotShield cookie (could be first-sight, could be stripping); E5 disambiguates the logged-in subset (definitely stripping) and flags harder because it carries information E4 can't see.

Out of scope for E5, may follow later:

  • POST /bs/feedback JSON endpoint for out-of-band reporting (e.g. from a background job that runs after the response was sent). Same HMAC key, same flag registry, additive with the header channel.
  • Early clear of existing flags. A credit bit (app_verified_*) composes with an existing penalty bit additively and both decay on their own TTLs; the plan deliberately does NOT let an app forcibly unset someone else's flag ahead of its expiry. Flag removal is a different, trickier primitive (atomic unset with concurrent-write semantics in the SHM table). The credit mechanism is sufficient for every use case that's come up so far.
  • Per-request score-only contributions (applied to this request only, no SHM write). Current model is "if it's worth feeding back, it's worth remembering across requests."

Score floor

Total effective flag penalty can go negative once credit bits exist (e.g. app_verified_human -80 with no offsetting penalties → -80 contribution). That's fine for tier dispatch — negative means "well below silent threshold, pass" — but worth bounding: clamp bs_flag_penalty output to a floor of -200 so a single gigantic credit bit can't lock out all future enforcement for that IP even if other signals later go bad. (Penalties are already unbounded above; there's no reasonable ceiling because high-trust penalty-stacking is a valid state.)

E6 — BotShieldEnvTrigger (Apache env-var bridge) (shipped)

General request-scoped env triggers. Another Apache module — or plain Apache config — sets a request env var, and BotShield consumes that as another policy source. The first proof case is ModSecurity v2, not v3: the current Apache v3 connector still documents itself as not production ready and recommends v2.9.x for Apache deployments.

That makes the real feature broader than "ModSecurity integration":

  • ModSecurity v2 setenv
  • SetEnvIf / SetEnvIfNoCase / SetEnvIfExpr
  • BrowserMatch / BrowserMatchNoCase
  • RewriteRule ... [E=VAR:VAL]
  • any future Apache module that writes request env before BotShield's handler runs

The guiding idea stays the same: BotShield should not learn another module's rule language or internals. It should just react to one coarse request-scoped signal.

Directive

BotShieldEnvTrigger <name> <env-match> [key=value ...]

<env-match> shapes (exactly one required):

env=<var>                  Environment variable is defined
                           on this request (any value,
                           including empty).
env=<var>=<value>          Environment variable exactly equals
                           the given value.
!env=<var>                 Environment variable is absent.

Keep matching deliberately simple in v1. No regexes here; if the operator wants regex matching, Apache/ModSecurity can do that upstream and set a coarse env bucket for BotShield to consume.

Action keys (same small policy surface as the other trigger families):

credit=<n> Subtract N from this request's score. Range 0..1000. Use sparingly; this is mainly a suspicious-signal feature, but a trusted upstream env marker can justify a credit. penalty=<n> Add N to this request's score. Same range. Primary use: suspicious signals. status=<code|pass> HTTP response on match. Default pass. Like E4, pass still applies the current- request credit / penalty because the env signal exists on this request. Use status=<code> when the env should short-circuit immediately. flag=<bit> M5.1 flag-IP bit for future requests. Same registry as E3/E4. ttl=<sec> Flagged-IP TTL. 0 = don't flag. log=<tag> Decision-log tag= field — same as E3.

Precedence

Match in declaration order, first match wins.

That keeps the rule easy to reason about and mirrors E3's operator idiom: specific before generic. If an operator wants several Apache conditions combined, they should set one combined env bucket upstream and let BotShield consume that one result.

Why env triggers instead of a ModSecurity-specific directive

  • Lets Apache config itself feed BotShield, not just ModSecurity.
  • Keeps BotShield decoupled from CRS rule ids, anomaly scores, and external module internals.
  • Makes "set a flag from Apache config" a first-class use case.
  • Still gives ModSecurity v2 a clean integration path — just not a privileged, one-off one.

Examples:

# ModSecurity v2: phase-1 anomaly buckets.
SecRule TX:ANOMALY_SCORE "@ge 5" \
  "id:100100,phase:1,pass,nolog,setenv:BS_MODSEC_MEDIUM=1"
SecRule TX:ANOMALY_SCORE "@ge 15" \
  "id:100101,phase:1,pass,nolog,setenv:BS_MODSEC_HIGH=1"

BotShieldEnvTrigger modsec-medium env=BS_MODSEC_MEDIUM \
    penalty=40 log=modsec-medium
BotShieldEnvTrigger modsec-high   env=BS_MODSEC_HIGH   \
    penalty=90 log=modsec-high

# Plain Apache config: obvious scraper UAs.
SetEnvIfNoCase User-Agent "curl|python-requests|wget" BS_SUSPECT_UA=1
BotShieldEnvTrigger suspect-ua env=BS_SUSPECT_UA \
    penalty=25 flag=scanner_probe ttl=3600

# Apache config: hostile net or explicitly banned subnet.
SetEnvIfExpr "-R '203.0.113.0/24'" BS_HOSTILE_NET=1
BotShieldEnvTrigger hostile-net env=BS_HOSTILE_NET \
    status=403 log="BAN 1d" flag=fake_bot ttl=86400

ModSecurity v2 as the first proof case

ModSecurity v2 remains the first concrete target because it already has the right hook model and its documentation explicitly describes setenv as creating env vars Apache can access. But it should be documented as the first producer, not the whole feature.

Phase split (still important):

  • Phase 1 / request-header signal ships first. This is the sweet spot for ModSecurity v2: same-request BotShield influence without forcing body work first.
  • Phase 2 / request-body signal is later and opt-in. Valuable on login/API POSTs, but no longer a "cheap early filter" story.

Semantics

  • Env table is r->subprocess_env. Apache's per-request env table that SetEnvIf, SetEnvIfExpr, BrowserMatch, RewriteRule [E=...], and ModSecurity v2 setenv all populate. BotShield reads it via apr_table_get; it never consults OS env (the CGI-boundary variant) from the request path.
  • Names and values are case-sensitive. Env var names in Apache's table are case-sensitive (POSIX semantics), as are values. env=FOO does not match a var named foo; env=FOO=Bar does not match value BAR. If operators need case-insensitive matching, set a coarse bucket upstream with SetEnvIfNoCase and consume that bucket here.
  • Producers run before bs_handler. All supported producers write to r->subprocess_env during Apache request phases that complete before the handler phase: SetEnvIf / SetEnvIfNoCase / BrowserMatch at header_parser; SetEnvIfExpr and RewriteRule [E=...] at fixups; ModSecurity v2 phase-1 setenv at header processing. So a bs_check_policy call in the handler phase observes whatever the upstream chain wrote. (Phase-2 ModSecurity body signals are deliberately deferred — they require request- body buffering decisions that belong in a later phase split.)
  • Main requests only. Gate on ap_is_initial_req(r) like E5 does. Apache's env propagation into subrequests is producer-specific (mod_setenvif behaves differently from mod_rewrite), and the right move is to apply env triggers exactly once per client-visible request rather than multiplicatively across subreq fan-out.
  • No redirect= key in this family (E3 and E4 have one). Env signals are about scoring/flagging/blocking, not response shaping. If an operator wants a redirect they can set it via a separate Apache redirect rule and let E6 do the flagging alongside.
  • Env match absent → trigger does nothing, zero cost.
  • Env match present → BotShield applies the trigger's configured current-request credit / penalty.
  • flag=<bit> + ttl=<sec> persists the effect in SHM for later requests, same as E3/E4/E5.
  • status=<code> short-circuits after applying the trigger's own bookkeeping/log/flag effects.
  • If the upstream producer already denied the request (e.g. disruptive ModSecurity rule), BotShield never sees it. This feature is for pass-through or Apache-config-driven signals.

Gate

  • Baseline request with no matching env var → unchanged BotShield score and decision.
  • Matching env trigger with status=pass → score shifts on the same request and the decision log carries the env-trigger reason.
  • Matching env trigger with flag= → flagged-IP state appears and affects the next request too.
  • SetEnvIf / BrowserMatch / RewriteRule [E=...] proof cases all work on the same request when configured on supported scopes.
  • ModSecurity v2 phase-1 setenv proof case works on the same request.
  • Later phase-2/body proof case is documented separately as opt-in.

Risks

  • Timing / phase ordering. The env var must exist before BotShield's handler makes its decision. Support is producer- specific and must be proved, not assumed.
  • Subrequest / internal-request quirks. Apache docs explicitly warn that some env mechanisms (notably mod_setenvif) behave differently for subrequests. Gate on the main request and test the supported producers carefully.
  • Config ambiguity. A request can be both "deny-worthy" to an upstream module and "challenge-worthy" to BotShield. Operators must decide which signals are disruptive and which are feedback-only.
  • Feature creep. This is not a general expression engine inside BotShield. Keep matching exact/presence-only and push rich logic upstream to Apache/ModSecurity.

Out of scope for E6:

  • Reading ModSecurity audit logs or parser internals.
  • Importing CRS rule ids / tags into BotShield and trying to understand them natively.
  • Request-body inspection in BotShield itself.
  • Regex/value-expression matching inside BotShieldEnvTrigger.
  • A v3-specific connector hack. If Apache ModSecurity v3 matures later, it can become another producer of request env.

E7 — Trigger family normalization (typed directives + shared action engine)

We now have enough trigger mechanisms that the public surface should be deliberate instead of accreted:

  • path triggers (BotShieldTrigger)
  • cookie triggers (BotShieldCookieTrigger)
  • env triggers (BotShieldEnvTrigger)
  • feedback/app-event triggers (today's E5 header channel)

The right shape is:

  • typed public directives
  • one shared internal action engine
  • explicit family-specific match semantics

and, because the module is still young enough to absorb config churn, no backward-compat alias is required. Rename the path directive cleanly and move on.

Public surface

BotShieldPathTrigger   <name> <path-glob>    [key=value ...]
BotShieldCookieTrigger <name> <cookie-match> [key=value ...]
BotShieldEnvTrigger    <name> <env-match>    [key=value ...]
BotShieldFeedbackTrigger <event>             [key=value ...]

BotShieldTrigger goes away. Path triggers are path triggers; call them that.

Do not collapse these into one mega-directive like:

BotShieldTrigger type=path ...
BotShieldTrigger type=cookie ...
BotShieldTrigger type=env ...

The match grammars are too different, the validation would get uglier, and the config becomes harder to read at a glance. Separate typed directives are the better public API.

Shared internal shape

Internally, though, they should stop being three nearly-separate policy islands.

Expected refactor:

  • one family-specific predicate parser per trigger kind
    • bs_path_trigger
    • bs_cookie_trigger
    • bs_env_trigger
    • bs_feedback_trigger
  • one shared action struct / parser for the common trigger actions
  • one shared executor for:
    • current-request credit
    • current-request penalty
    • status=<code|pass>
    • flag=<bit>
    • ttl=<sec>
    • log=<tag>
  • one shared redirect helper for the families that support it (currently path + cookie; env remains score/flag/block only unless a later use case proves redirect semantics are worth adding there too)

This does not mean "expose every internal scoring knob." The shared action surface stays intentionally small. Triggers may nudge score, set persistent reputation bits, and short-circuit with a response; they do not get a raw handle on the whole scoring engine.

Feedback triggers are the one family that intentionally support only the future-request memory subset. The app has already served the response; E5 should map a signed event name to BotShield memory, not retroactively rewrite the current request's outcome.

Family-specific semantics stay explicit

The refactor should unify the plumbing without flattening important behavior differences away.

In particular:

  • BotShieldPathTrigger status=pass
    • no current-request credit / penalty
    • pass-through request; later-request memory comes from flag=<bit> + ttl=<sec>
  • BotShieldCookieTrigger status=pass
    • current-request credit / penalty still apply
    • because the client is actively carrying the cookie signal on this request
  • BotShieldEnvTrigger status=pass
    • same semantic as cookie triggers
    • the request env is present on this request, so the score effect belongs on this request too
  • BotShieldFeedbackTrigger
    • response-path only
    • no current-request credit / penalty
    • no status=<code|pass>
    • no redirect=<url>
    • only maps a signed app event into future-request state, e.g. flag=<bit> + ttl=<sec> + optional log=<tag>

That means the shared executor probably wants a small family-level "semantic profile" rather than one blindly uniform rule.

Cross-family ordering

Once there is a typed family, define the policy walk order explicitly:

  1. cookie triggers
  2. env triggers
  3. path triggers
  4. feedback triggers (response path, separate hook, not part of the request-time bs_check_policy walk)

Rationale:

  • cookies are client-carried ongoing state
  • env triggers are upstream/app/Apache state about this request
  • path triggers are the one-off "you touched this path" events
  • feedback triggers are app-originated events that only affect later requests

Any request-time family may short-circuit. Once one trigger returns a real response, later request-time families do not run. Feedback triggers are separate because they run on the response path after the app has already handled the request.

Within a family, keep the current rule:

  • declaration order
  • first match wins

Reason/log vocabulary

Normalize the decision-log / reason strings while doing the refactor. Today the trigger family names are implicit in too many places.

Preferred shape:

  • path-trigger:<name>:<n>
  • cookie-trigger:<name>:<n>
  • env-trigger:<name>:<n>
  • feedback-trigger:<event>

and the existing tag= behavior stays shared across all three.

E7.1 — public rename (shipped)

  • BotShieldTrigger renamed to BotShieldPathTrigger
  • docs/examples/tests updated to use the typed family names
  • no compatibility alias

Gate:

  • fresh config uses the three typed directives only
  • help text and docs read as one coherent trigger family, not three unrelated features

E7.2 — shared action engine (shipped)

  • one parsed action struct
  • one executor for scoring / flagging / logging / status, plus the shared redirect helper for the families that support it
  • family-specific matchers feed that executor
  • feedback trigger executor uses only the allowed subset (flag / ttl / optional log)

Gate:

  • path/cookie/env triggers expose the same action vocabulary where it makes sense
  • feedback triggers reuse the same internal action plumbing where it makes sense without pretending response-path app events are the same as request-time predicates
  • family-specific semantic differences around status=pass stay covered by tests

E7.3 — dispatch/order cleanup (shipped)

  • explicit family order in bs_check_policy
  • normalized reason strings
  • common documentation for precedence and short-circuit behavior
  • E5 header channel becomes event=<name>;sig=<hex> and maps through BotShieldFeedbackTrigger <event> ... instead of shipping raw flag= / ttl= policy in the header body

Gate:

  • cookie/env/path ordering is deterministic and tested
  • later trigger families do not run after an earlier short-circuit
  • decision logs show which family fired without operators having to infer it from context
  • feedback events are signed, stripped before send, and mapped by config, not by app-supplied raw BotShield policy fields

Risks

  • Config churn. Renaming BotShieldTrigger is a real breaking change; do it now or never.
  • False uniformity. Internal unification must not erase real differences in trigger semantics.
  • Action creep. A shared engine makes it tempting to expose every internal knob everywhere. Resist that.
  • E5 migration complexity. Moving from flag= / ttl= in the signed header body to event=<name> is the right design, but it is still a wire-format change for the app side and should be treated explicitly.

Out of scope for E7:

  • backward-compat aliases for old trigger names
  • one generic trigger DSL
  • exposing every internal heuristic as its own trigger action
  • trigger-time mutation of provider/algorithm selection or other deep internals

E8 — Cookie confidentiality (AES-GCM migration)

Replace the current HMAC-SHA-256 cookie envelope with AES-256-GCM so the cookie body is confidential, not just integrity-protected.

Today _bs_verified is base64-encoded + HMAC-signed. That proves the cookie hasn't been tampered with, but anyone base64-decoding the payload reads every field in cleartext — protocol version, algorithm, difficulty, expiry, PoW counter, and the rep block (rep_silent_passes, rep_form_passes, rep_captcha_passes, and the flag-bitmap snapshot). That last field is the reason to care: it tells the cookie holder which flag bits they've tripped (honeypot_hit / scanner_probe / fake_bot / pow_fail_streak), which is actionable intel for an attacker trying to adapt. Everything else is arguably operational state the client already knows.

As long as the rep block stays a short aggregate snapshot the current exposure is bounded — the flagged-IP table and the HMAC secret both live in SHM, the cookie is just a convenience payload. Pressure to encrypt rises as soon as we put richer behavior history in the cookie: last-N decision reasons, per-flag TTLs, E4's future HMAC-claim layer, any per-request reason trace.

Primitive

AES-256-GCM via libcrypto (already linked for HMAC). Authenticated encryption in one pass, so it replaces the HMAC leg rather than layering on top — no double crypto. Microsecond cost per request on modern CPUs (AES-NI / ARMv8-crypto). Wire format grows by ~12 bytes (12-byte nonce + 16-byte tag minus the 16-byte HMAC tag we already carry).

ChaCha20-Poly1305 is a reasonable alternative on hardware without AES acceleration. Pick one at implementation time; the wire format should carry a small algorithm byte so we can swap later without another migration.

Wire format (proposed)

<alg-id:1 byte> <nonce:12 bytes> <ciphertext:N> <tag:16 bytes>

base64url-encoded, no padding, to keep the cookie URL-safe.

alg-id lets us run more than one algorithm simultaneously during a deprecation window or key rotation.

Migration strategy

Wire-format change means any cookie issued before the upgrade would fail decryption on the upgraded server. That's recoverable (the client re-challenges and gets a fresh cookie) but still a visible blip operators should plan around.

Ship behind a compat switch with dual-verify:

BotShieldCookieFormat gcm            # issue + verify AES-GCM only
BotShieldCookieFormat gcm,hmac       # issue GCM, accept either
BotShieldCookieFormat hmac           # legacy; issue + verify HMAC only
                                     # (default until operators opt in)

Typical upgrade path:

  1. Operator sets BotShieldCookieFormat gcm,hmac, reloads. New cookies are GCM; old cookies still validate. No user impact.
  2. After whatever the operator's longest cookie TTL is, all live cookies have cycled to GCM. Operator flips to BotShieldCookieFormat gcm and removes HMAC verify.
  3. Eventually the HMAC code path is dropped from the module entirely.

Key file stays the same (BotShieldSecretFile). For GCM we treat it as the AES key (first 32 bytes); the HMAC code uses the same file. No new secret-management surface for operators.

Out of scope for this extension

  • Key rotation. Needs a multi-key verify + keyed-issue model. Reserve an algorithm-id slot for "AES-GCM with kid=" and plan the rotation story when a real operator asks for one. Separate feature.
  • Server-side session. The whole reason the cookie is self-contained is to avoid needing a session store. Encryption doesn't change that tradeoff; if a future feature needs real secrets in a cookie, the right move is opaque bearer + server state, not "encrypt a bigger blob."
  • Per-client keys. Single symmetric key is fine for cookie confidentiality; the HMAC secret is already single-tenant.

When to build this

Not yet — no clients using the module yet, so the wire-format break is free whenever we do the work. The prompt will be whichever future feature first tries to stuff more behavioral detail into the cookie. At that point E8 becomes a blocker, not an enhancement.

E9 — Repeated-429 escalation (short-lived rate-limit hardening) (shipped)

This is a follow-on to E2's rate-limit machinery, but it lands later in the roadmap because E2 itself is already shipped. A client that keeps hitting BotShield-generated 429 responses without changing behavior is a stronger signal than generic 4xx noise. This is not "the client burst once"; it is "the client was explicitly told to slow down and kept going anyway."

Teach the rate-limit layer one extra step:

  • first threshold: normal E2 rate limit (429 + Retry-After)
  • second threshold: repeated ignored 429s promote the client into a short-lived harder state for that same rule, typically 403

This still belongs conceptually with rate limiting, not with the generic trigger families. The signal is stateful and BotShield- generated: "how many times did this client hit this named rate limit badly enough that we returned 429?"

Directive shape:

BotShieldRateLimitEscalate <rate-name> <strikes> <per> [key=value ...]

Supported keys:

status=<code> HTTP status to return once the escalation threshold is crossed. Default: 403.

ttl=<sec> How long the escalated state lasts after the last strike. Keep this intentionally short-lived (minutes, not days). Default: 1800.

log=<tag> Optional distinctive decision-log tag emitted when the escalation threshold is crossed. Intended for external tooling such as fail2ban. Example: log="BAN rate-limit-abuse".

Runtime shape:

  • dedicated bounded SHM strike table keyed by (client_ip, rate_rule_id); do not reuse the approximate fixed-window cohort counters for punitive decisions
  • increment only when BotShield itself emits 429 from an E2 rate limit (directive BotShieldRateLimit or robots.txt Crawl-delay)
  • once the strike threshold is crossed, subsequent requests that match the same rate rule return the configured escalated status until the TTL expires
  • expiry is automatic; this is immediate adaptive protection, not a long-term ban system

Why this shape:

  • keeps memory bounded on very high-traffic sites
  • avoids broad IP-wide punishment when the abusive behavior is local to one named rate-limited policy
  • gives operators a clean handoff point to fail2ban or similar systems when they want longer-lived firewall bans

Non-goal: BotShield does not become a permanent ban manager here. If an operator wants multi-hour or multi-day consequences, the intended path is: BotShield logs a stable escalation tag, and fail2ban (or an equivalent external system) turns that into a longer network-level ban.

Deliverables:

  • BotShieldRateLimitEscalate directive + per-rule config object
  • bounded SHM strike table allocated alongside the other E2 policy state; fixed slot count, no unbounded per-client growth
  • request-time check in the E2 rate-limit path: normal 429 first, escalated status=<code> after the configured repeated-429 threshold
  • reason strings / metrics for escalated hits (for example rate-limit-abuse:<name> and botshield_rate_limit_escalated_total)
  • pytest coverage for: repeated 429 → escalated 403; expiry back to normal 429; tag emitted on threshold crossing (fail2ban-friendly path)

Known interaction (parked for future): rate-limit budgets are per-cohort (one bucket per rule, shared across all matching IPs), but strike accounting is per-(IP, rule). If two clients share a busy cohort, IP-A consuming the whole budget can cause IP-B's benign requests to 429 and tick IP-B's strike counter through no fault of IP-B's. Edge-y enough not to address yet — would surface as an operator complaint with tight strike thresholds against a heavily contended cohort. Resolution path is per-IP rate-limit scope (scope=ip flag on BotShieldRateLimit allocating a per-IP bucket), which is its own feature rather than a tweak to E9.

E10 — Challenge safeguard / anti-loop hysteresis (shipped)

BotShield is good at adding friction. It still needs a clean answer for the opposite failure mode: a borderline-real client gets stuck in repeated silent-challenge or captcha churn because of CSP, blockers, broken JS, privacy tooling, or some other integration edge case.

The goal is not to grant trust. The goal is to stop pointless looping and choose a deterministic lower-churn behavior for a short window.

Core idea:

  • track recent challenge presentations and outcomes per client
  • if BotShield keeps presenting the same sort of challenge and the client never progresses to _bs_verified, trip a short-lived safeguard state
  • while safeguard is active, suppress repeated re-presentation of the same challenge path and log that this happened

This is especially relevant once E17 exists, but it is also useful for today's interstitial flow.

V1 should stay conservative:

  • safeguard is not a trust grant and does not mint _bs_verified
  • safeguard is short-lived
  • safeguard should never override a clear hard block / deny decision
  • the main effect is "stop hammering this client with the same challenge loop"

Reasonable runtime shape:

  • bounded SHM or cookie-backed recent-challenge state
  • a threshold like "N presentations in W seconds with no solve"
  • short safeguard TTL (for example 5–15 minutes)
  • reason / metric such as challenge-safeguard and botshield_challenge_safeguard_total

Policy while safeguard is active:

  • for silent/embedded flows: stop reinjecting the wrapper on every page view for the safeguard window
  • for visible/interstitial flows: avoid redirect/rechallenge churn and return a stable non-looping outcome instead

The exact fallback can be tuned later, but the invariant should be: no endless challenge loop and no silent trust grant.

Deliverables:

  • bounded recent-challenge tracking
  • short-lived safeguard state
  • request/response-path checks that suppress repeated challenge loops
  • metrics/logging so operators can see when this path is being used
  • pytest/browser coverage for repeated-failure loop scenarios

E11 — Load-aware throttling (BotShieldLoadTrigger) (shipped)

This is origin overload protection, not generic DoS/DDoS defense. The job is to help Apache shed low-trust or high-cost traffic when the server is running hot, without turning BotShield into a full host-health agent.

Core idea:

  • BotShield samples a few coarse load signals
  • derives a cached load state such as normal, warm, hot
  • applies configured policy only while the site is under pressure

The important constraint: requests should read a cached load state. They should not scan the Apache scoreboard or compute moving averages on every request.

Signal sources

Use up to three sources together:

  1. Apache scoreboard snapshot for current saturation.
  2. BotShield-owned short time buckets for recent request pressure.
  3. Optional external load-state file for operator / monitor override.

Apache can already expose most of what matters here via the public scoreboard API:

  • worker states (READY, BUSY_READ, BUSY_WRITE, BUSY_KEEPALIVE, BUSY_LOG, CLOSING, GRACEFUL)
  • async-process pressure such as connections, keep_alive, write_completion, and not_accepting

BotShield should add its own tiny SHM request counters in a few fixed buckets (for example 1s / 10s / 60s) so it can see trend, not just the current worker snapshot.

For the external-input path, do not invent a request-by-request bridge through Apache config. If an external monitor already knows the site is overloaded, the cleanest handoff is a tiny watched state file, for example:

/run/botshield/load.state  ->  normal | warm | hot

BotShield can poll this through the same mod_watchdog pattern already used for robots refresh: stat first, re-read only on change, cache the parsed enum, and let requests read the cached state cheaply.

What BotShield should not do in v1:

  • poll host CPU load average
  • inspect free memory
  • scrape /server-status
  • become a general machine-health monitor

Runtime shape

  • watchdog / timed callback samples the Apache scoreboard periodically (for example once per second)
  • optional watchdog / timed callback also polls the external load-state file (mtime-gated, same pattern as robots.txt refresh)
  • BotShield updates fixed-size request-rate buckets on the request path
  • sampler derives a small cached load state with hysteresis (normal → warm → hot, and back down more slowly)
  • when both internal sensing and an external state file are present, the most severe state wins
  • requests read only that cached state and the normal BotShield trust/suspicion signals

Useful derived signals:

  • busy worker ratio
  • idle worker count
  • async connection pressure
  • recent request burst rate
  • optional consecutive-hot-samples count to avoid flapping

Directive surface

BotShieldLoadTrigger <name> <load-match> [key=value ...]

BotShieldLoadStateFile /run/botshield/load.state
BotShieldLoadRefreshInterval 1

Examples of load-match:

state=warm
state=hot
state>=warm

The external state file should stay deliberately tiny in v1:

  • normal
  • warm
  • hot

No bespoke parser language, no percentages, no timestamps in the first cut. If operators need richer semantics later, that can be added after the simple override path proves useful.

Action keys should stay inside the existing small BotShield action surface:

  • credit=<n>
  • penalty=<n>
  • status=<code|pass>
  • log=<tag>

This is not meant to bypass the rest of the policy engine. The usual use is:

  • stricter treatment for first-sight / unverified / botlike traffic
  • optional short-circuiting of expensive anonymous paths
  • gentler handling for already-verified or explicitly-allowed traffic

Policy shape

The safe mental model is brownout mode, not panic mode.

Under warm / hot load, BotShield should help the site preserve capacity by getting more aggressive against:

  • unverified clients
  • first-sight clients
  • botlike traffic
  • expensive paths

and avoid punishing obviously legitimate / already-verified traffic unless the operator explicitly configures that.

Deliverables

  • bounded SHM request-rate buckets (short windows only)
  • scoreboard sampler using the public Apache scoreboard API
  • optional external load-state file support using mod_watchdog polling and cached enum state
  • cached load-state computation with hysteresis
  • BotShieldLoadTrigger directive + request-time matcher
  • metrics for current load state transitions / load-trigger hits
  • pytest / stress coverage proving:
    • state moves from normal → warm / hot under synthetic load
    • external state file can force warm / hot
    • "most severe wins" when internal and external inputs disagree
    • request path reads cached state only
    • state recovers cleanly without oscillating wildly

E12 — Shadow mode / dry-run enforcement (shipped)

BotShield is increasingly policy-rich. Operators need a safe way to roll out new rules without immediately blocking real traffic.

The goal of E12 is simple: let a policy match and log exactly what it would have done without actually enforcing it.

This should work for the main policy families:

  • E2 rate limits / block paths
  • E3 path triggers
  • E4 cookie triggers
  • E6 env triggers
  • E11 load triggers

Core behavior:

  • rule matches as normal
  • BotShield records a stable "would have enforced" reason/tag
  • no disruptive action is taken
  • optional score/flag side effects are either suppressed entirely or clearly split into "observe-only" and "enforce" modes

V1 should stay conservative and easy to explain:

  • "observe" means no response-shaping and no persistent memory
  • request remains otherwise normal
  • logs / metrics clearly distinguish real enforcement from dry-run

Possible directive shapes:

BotShieldShadowMode on

or per-rule:

BotShieldPathTrigger trap "/.env" mode=observe status=403 log=shadow-env

The per-rule shape is more flexible and probably the better long-term fit, but either way the invariant should be: operators can stage policy safely and see real match volume before turning enforcement on.

Deliverables:

  • observe-only policy mode for the trigger / rate-limit families
  • decision-log vocabulary such as would-block, would-rate-limit, would-flag
  • metrics separated from real enforcement counters
  • pytest coverage proving observe-mode matches log but do not enforce

E13 — State namespacing / multi-vhost isolation (shipped)

Today BotShield's SHM-backed reputation state is module-global:

  • flagged-IP table
  • Bloom filter
  • any future shared reputation/state built on the same keying

That is excellent for one organization running several related sites, but wrong for true multi-tenant or strongly isolated multi-app deployments.

E13 makes that boundary explicit.

Core idea:

  • keep the shared SHM machinery
  • optionally namespace the SHM lookups by a per-scope token
  • requests in different namespaces stop sharing flagged-IP / Bloom reputation

As shipped — design pivoted from the original "default-share / opt-in isolate" sketch to default-isolate / opt-in share because targeting production sites with multiple vhosts means the safer default is "different vhosts don't pool reputation unless told to":

  • each vhost auto-isolates by siphash(ServerName) at post_config
  • BotShieldShareScope <token> is the opt-in to share across vhosts (two vhosts that set the same token compute the same ns_id and pool reputation)
  • a missing ServerName AND missing BotShieldShareScope falls back to ns_id=0 (a server-wide global namespace) with a NOTICE in the error log so operators can spot the unintended sharing

Implementation:

  • single SHM segment retained — no per-vhost segments, no segment count to size
  • ns_id (apr_uint32_t) added to every reputation slot: flagged-IP, strike, safeguard
  • ns_id mixed into siphash inputs for flagged-IP / strike / safeguard / Bloom bucket selection so different namespaces get disjoint bucket distributions and the K=7 Bloom probes are independent across namespaces
  • lookups reject slots whose ns_id doesn't match
  • writes record the calling vhost's ns_id on the slot
  • BS_STATE_FORMAT_VERSION bumped 1→2; old (v1) state files are rejected with a NOTICE and the table starts fresh — slot layout changed and a slot-level migration would have to fabricate ns_id values, which is more dangerous than letting the table rebuild from live traffic
  • BS_DEFAULT_SHM_SIZE bumped 8M→16M to absorb the extra 8 bytes per slot across the four reputation tables at default capacities
  • follow-up — empty-marker consistency cleanup (subsequent commit): every SHM slot type now carries an explicit apr_uint32_t used field where 0 == empty, replacing the per-table sentinel-value tricks (flags == 0, rule_slot == BS_STRIKE_EMPTY, expires_at == 0). bs_flagged_ip_slot was reordered to fit the new field in the prior _pad slot (size unchanged at 40 bytes) and BS_STATE_FORMAT_VERSION bumped 2→3. Slot bytes from v2 state files don't map cleanly into v3 layout, so older files are rejected with a NOTICE and the table starts fresh — same posture as the v1→v2 bump

Deliverables (shipped):

  • BotShieldShareScope directive (default-isolate, opt-in share)
  • ns_id mixed into flagged-IP / strike / safeguard / Bloom keying
  • bs_warn_if_virtual_scope NOTICE on every SHM-sizing directive placed inside <VirtualHost> (BotShieldShmSize, BotShieldFlaggedIPCapacity, BotShieldBloomIPs, BotShieldBloomWindow, BotShieldRateLimitEscalateCapacity, BotShieldSafeguardCapacity)
  • pytest coverage in tests/pytests/test_namespace.py proving isolated namespaces do not share flagged-IP reputation across a config reload, and that within one namespace the flag survives a reload via the persisted state file

Deferred:

  • BotShieldCookieName for per-app cookie separation. The verified cookie is already namespaced via the HMAC secret (different vhosts can configure different BotShieldSecretFiles) and the cookie is bound to its issuing host by the browser, so the cross-app cookie pollution risk that motivated this deliverable is largely already mitigated. Revisit if a real operator hits the edge case.

E14 — Adaptive challenge intensity (shipped)

Today BotShield's friction level is mostly threshold-driven:

  • pass
  • silent
  • form
  • captcha

That is good, but static. E14 adds a narrow adaptive layer so the module can change how hard it pushes back based on what it already knows about the client or the server state.

Good inputs for adaptation:

  • flagged-IP state
  • repeated challenge failures
  • repeated PoW failures
  • E11 load state (warm / hot)
  • expensive-path scope

V1 should stay intentionally boring:

  • raise PoW difficulty for some classes of traffic
  • escalate silent → form or form → captcha under configured conditions
  • never silently downgrade a clearly hard-blocking condition

This is not "AI difficulty." It is just a more expressive mapping from existing BotShield signals to the existing challenge ladder.

Possible directive shape:

BotShieldAdaptiveChallenge <name> <predicate> [key=value ...]

or a smaller first cut:

BotShieldDifficultyTrigger <predicate> difficulty=5

The exact syntax matters less than the policy boundary:

  • reuse existing trust / score / flag / load state
  • adjust challenge intensity
  • keep the result explainable in logs and status output

Deliverables:

  • a small adaptive-difficulty / adaptive-tier policy layer
  • reason strings that surface why intensity changed
  • tests covering raised PoW difficulty and tier escalation under configured predicates

As shipped — design landed on flag-registry rather than a new predicate language, after weighing the cost of duplicating the trigger predicate engine against the simplicity of binding adaptive metadata to the existing flag-bit names that every writer already uses:

  • new directive BotShieldFlag <name> [penalty=N] [next_difficulty=±N] [next_tier=pass|silent|form|captcha] overrides registered flag-bit metadata. Operators declare the policy once at the flag-name level; every writer that sets the bit (BotShieldFlagIP, BotShieldFeedbackTrigger flag=, env-trigger flag actions, the scope-honeypot mechanic) inherits the adaptive consequences for free
  • BotShieldMaxDifficulty <N> (server-scope, 1..16, default 8) bounds the effective PoW difficulty after adaptive bumps
  • request path computes bs_flag_adaptive_for(flags) against both IP-side flags and cookie-side flags. next_difficulty SUMs across set bits; next_tier takes MAX. Score-derived tier wins when it's already higher than the floor — never silently downgrades
  • effective applied delta lands in the reason chain as adaptive-difficulty:+N (post-clamp value, not the raw config) and the adaptive tier-floor surfaces as adaptive-tier:<tier> when it pushes the request above what score alone would have produced
  • credit flags (app_verified_human etc.) can declare negative next_difficulty so trusted clients get cheaper challenges if any ever land — tested via the clamp-to-floor path

Deferred from PLAN's broader vision:

  • per-trigger-action difficulty= / tier= keys directly on BotShieldPathTrigger etc. for one-off bumps that don't go through a flag bit. The flag-registry covers the headline feedback-driven use case; per-trigger keys land in V2 only if operators ask
  • a dedicated BotShieldDifficultyTrigger predicate-language. Same reasoning — overlaps the existing trigger families and the flag registry already routes most use cases

Deliverables (shipped):

  • BotShieldFlag directive + per-flag metadata storage
  • BotShieldMaxDifficulty server-scope ceiling
  • request-path adaptive accumulator, clamp, and reason emission
  • pytest coverage in tests/pytests/test_adaptive_intensity.py: directive validation (4), tier-floor escalation, tier-floor doesn't-downgrade, difficulty bump appears in reasons, difficulty clamp to default ceiling, max-difficulty raises ceiling, default config emits no adaptive reasons

E15 — Forgiveness cap per rolling window (shipped)

The cookie-rep score model gives a small forgiveness credit each time a client passes a challenge — it lets a borderline-suspicious real user keep transacting after solving once. The intent is that forgiveness offsets transient suspicion, not that it erases a genuinely accumulated rep score.

Without a ceiling, a patient adversary can convert that into forgiveness farming:

bot pinned at score ≈ silent-threshold
→ solves PoW once every few minutes
→ each pass subtracts forgive_silent (≈10) from cookie rep
→ score never accumulates

At ≈ 10 points per pass and one pass every 5 min, that's ~120 pts per hour drained off the rep score — easily enough to neutralize heuristic accumulation that would otherwise tier them up.

Goal of E15: bound how many forgiveness points one cookie can collect inside a rolling 1-hour window, without breaking the real user's "solve once, transact for an hour" experience.

Where to track the consumed counter is the load-bearing design question:

  • Per-IP SHM table survives cookie drops but adds another reputation table (memory growth) and inherits the IP-rotation evasion shape we already accept for flagged-IP.
  • Per-cookie envelope is simpler — counter + window-start ride in the cookie state we already mint and verify. Bot drops cookie → counter resets but ALSO drops the score-debt forgiveness was meant to whittle down, so cookie-rotation is no escape.

V1 chose per-cookie. Two new fields in bs_rep_state, forgive_window_start (unix sec) + forgive_consumed (u32). Cookie protocol bumped 1→2.

Possible directive shape:

BotShieldForgivenessCapPerHour 200

Range 0..1000 with 0 disabling the cap (legacy uncapped). 200 is a real-user-friendly default — enough headroom for a borderline user to clear several challenges in an hour, tight enough to render forgiveness farming uneconomic.

Deliverables (shipped):

  • bs_rep_state grows forgive_window_start + forgive_consumed, both serialized into the cookie envelope with a one-time BS_PROTOCOL_VERSION 1→2 bump
  • bs_forgiveness_apply_cap() rolls the rolling-hour window when

    = 3600 s have elapsed since window_start, clamps the requested forgiveness so consumed never exceeds the cap, and returns the granted amount

  • BotShieldForgivenessCapPerHour <0..1000> server-scope directive, default BS_DEFAULT_FORGIVE_CAP_PER_HOUR = 200
  • both forgiveness-apply call sites (form/silent path in bs_handler; captcha-success path in the verify handler) route through the helper
  • form/silent path emits forgive-capped:granted/requested in the reason chain when the cap kicks in, so operators can spot real users hitting the ceiling and tune
  • pytest coverage in tests/pytests/test_forgive_cap.py: directive validation (negative, out-of-range, 0 disables, normal value)

The end-to-end "bot solves N times and gets capped after the cap" behavior isn't pytested directly because driving N real-PoW solves sequentially is slow and the cookie-state inspection that would need is not currently exposed. The directive-validation tests plus the unit-level helper logic (clamp + window roll) are the load-bearing coverage.

E16 — Cookie secret rotation (verify-only secondary key) (shipped)

BotShieldSecretFile is the HMAC/GCM key behind every minted _bs_verified cookie. There was previously no provision to rotate that key gracefully — operators replacing the file invalidate every active cookie at once and force a re-challenge wave. Bad operator hygiene was the friction keeping rotation from happening.

E16 lets the operator stage a graceful swap:

  1. Operator generates the new key file. Moves the OLD key to a secondary path. Sets BotShieldSecretFile to the new key, BotShieldSecondarySecretFile to the OLD key. Reload Apache.
  2. Verify path now accepts cookies signed under EITHER key. Issue path always uses the new key, so fresh challenges produce new-key cookies.
  3. After one BotShieldCookieTTL window, every active cookie has been re-issued under the new key.
  4. Operator drops the BotShieldSecondarySecretFile directive and reloads. Old cookies expired naturally.

The cookie envelope deliberately does NOT carry a kid field — both HMAC verify (constant-time compare against expected sig) and GCM verify (authenticated decryption with a known key) are cheap enough that trial-and-error is fine. Adding kid would have meant another protocol-version bump and a forced re-challenge wave; the trial-and-error cost is one extra HMAC-SHA-256 (or one extra GCM-decrypt attempt) per cookie that fails the primary key — and during a rotation window most cookies still verify under the primary in their first attempt.

Possible directive shape:

BotShieldSecondarySecretFile /etc/botshield/secret.old

Same per-scope inheritance, same mode-0600 hygiene, same minimum length (16 bytes) as the primary.

Deliverables (shipped):

  • bs_dir_cfg gains secret_secondary + secret_secondary_len alongside the primary; merges follow the same "child-set wins" pattern
  • HMAC verify in bs_verify_cookie_hmac tries primary first, then secondary on signature mismatch (only if a secondary is configured)
  • GCM verify in bs_verify_cookie_gcm tries primary first, then secondary on tag failure. AES-GCM's authenticated decryption guarantees the wrong key fails cleanly without leaking plaintext, so the retry is safe
  • issue path is unchanged — always uses the primary key
  • BotShieldSecondarySecretFile directive (per-scope, RSRC_CONF | ACCESS_CONF), with the same world-readable / mode-600 / minimum- length checks as BotShieldSecretFile
  • pytest coverage in tests/pytests/test_secret_rotation.py: directive validation (missing file, world-readable, well-formed, primary-key path doesn't break with secondary configured)

End-to-end "cookie signed under the old key still validates after rotation" requires writing two real secret files and minting a cookie under each, which the test framework's config_override pattern can do but is heavier than the directive-level coverage shipped here. The unit-level fall-back logic (HMAC retry on secondary in bs_verify_cookie_hmac; GCM retry on secondary in bs_verify_cookie_gcm) is the load-bearing correctness guarantee.

E17 — Embedded silent verification wrapper (provider adapters + native mode)

The "app adds one BotShield script tag and silent verification happens in the background" extension. The first draft of this plan assumed one native DOM-probe challenge from day one; that's too speculative. The right shape is a stable BotShield-facing wrapper with provider-specific adapters underneath, shipped one provider class at a time. If the abstraction bends too far, we stop and split it; we do not promise a perfect universal silent mode up front.

Core idea:

  1. Operator enables E17 on a scope and adds one BotShield script tag to the page template, e.g. <script src="/botshield/embedded.js" defer></script>.
  2. Silent-tier request still serves the real page immediately. No splash, no output filter, no markup rewriting by the module.
  3. embedded.js learns the configured adapter for that scope (provider-backed or native), loads any extra provider assets it needs, and runs the background/invisible verification flow.
  4. The wrapper POSTs the resulting token / score artifact back to a BotShield endpoint under BotShieldEndpointPrefix.
  5. BotShield verifies the result — by reusing the existing M8 provider siteverify path where possible, or by using its own native verifier for a future built-in mode — then issues the normal _bs_verified rep cookie.
  6. The next request rides through DECLINED.

This keeps the app-facing integration stable even if the underlying provider changes. The app owner integrates BotShield, not Turnstile-vs-hCaptcha-vs-reCAPTCHA-v3-vs-native separately.

Important boundary: E17 is not a promise that every provider has identical UX. Some providers are invisible token issuers, some are score-based, some may still escalate visibly for risky clients. E17 only promises one BotShield wrapper and one BotShield verify path.

Config sharing with interstitial mode

Yes — the default assumption should be that E17 shares the existing interstitial/provider verification config unless and until a real use case forces a split.

Server-side config to reuse by default:

  • BotShieldCaptchaProvider
  • BotShieldCaptchaSiteKey
  • BotShieldCaptchaSecretFile
  • BotShieldCaptchaTimeout
  • BotShieldCaptchaExpectedHostname
  • BotShieldCaptchaExpectedAction
  • BotShieldRecaptchaV3MinScore
  • existing provider-registry metadata such as verify URLs and provider script/widget URLs

That means the first provider-backed E17 adapters should sit on top of the same M8 provider rows and the same siteverify shims. Do not create a second parallel provider registry for "embedded mode."

New E17-only config is only for the wrapper/orchestration layer:

  • whether silent tier uses M7 interstitial or E17 embedded flow
  • where the BotShield wrapper JS is served from
  • where the embedded verify endpoint lives
  • optional asset-URL overrides if an operator needs to self-host or pin provider JS
  • eventual native-mode selection

Design rule: one provider config by default across interstitial and embedded on the same scope. If someone later needs "Turnstile interstitial but Friendly embedded" or similar, add an explicit override only after a real operator use case appears.

Candidate directive surface

Do not freeze this too early; E17 exists precisely because we are not yet sure how uniform the adapters can be. But the expected split is:

BotShieldSilentMode          interstitial | embedded   # default interstitial
BotShieldEmbeddedScriptURL   /botshield/embedded.js
BotShieldEmbeddedVerifyURL   /botshield/embedded-verify
BotShieldEmbeddedAssetURL    default | <url>
BotShieldEmbeddedNativeMode  off | pow                 # default off

Deliberately not adding embedded-specific copies of:

  • BotShieldCaptchaProvider
  • BotShieldCaptchaSiteKey
  • BotShieldCaptchaSecretFile

unless E17.2/E17.3 prove that shared config is too constraining.

Wrapper contract

The BotShield wrapper is the stable app-facing API. Internally it may dispatch to different adapters, but the page should only need one integration pattern:

  1. App includes embedded.js.
  2. Wrapper discovers the configured mode for the current scope (inline data-* attributes or a tiny JSON bootstrap — pick one during E17.1, not both).
  3. Wrapper loads the provider asset if needed, or runs the native adapter if no third-party asset is required.
  4. Wrapper obtains a token / score / proof artifact.
  5. Wrapper POSTs it to BotShield.
  6. BotShield verifies and sets _bs_verified.

Cap-like self-hosted systems fit here only as another adapter. They are provider-style backends, not the definition of E17.

Per-response activation model

The wrapper may be included on every page without challenging on every page. Loading embedded.js globally is fine; the wrapper must be a cheap no-op unless BotShield marks this specific response as needing embedded verification.

Expected shape:

  1. Page includes embedded.js unconditionally.
  2. BotShield emits a tiny per-response bootstrap signal only when the current request landed in an E17-enabled tier.
  3. Wrapper checks for that signal on load.
  4. No signal → wrapper exits immediately; no provider asset loaded, no background work, no POST back to BotShield.
  5. Signal present → wrapper sees:
    • mode=off|silent|visible
    • provider=<name>|native
    • whatever nonce/token/bootstrap fields the adapter needs
    • BotShield verify URL
  6. Only then does the wrapper lazy-load provider assets or run the native adapter.

Representative bootstrap shape (exact transport chosen in E17.1):

window.BotShieldEmbedded = {
  mode: "off" | "silent" | "visible",
  provider: "turnstile" | "hcaptcha" | "recaptcha-v3" | "native",
  verifyUrl: "/botshield/embedded-verify",
  nonce: "..."
};

Initial scope recommendation:

  • mode=off — default on ordinary responses; wrapper exits.
  • mode=silent — the real E17 v1 target. Wrapper runs background verification and BotShield sets _bs_verified.
  • mode=visible — optional later. Do not assume E17 v1 must own the full visible-captcha UX; keeping hard-tier captcha on the existing M8 interstitial path is acceptable until a provider-backed embedded visible flow is proven worth it.

E17.1 — wrapper foundation

Ship the BotShield-owned shell before promising any real provider coverage:

  • module endpoint for embedded.js under BotShieldEndpointPrefix
  • module endpoint for embedded verify POSTs
  • tiny per-scope bootstrap config (script data-* vs JSON endpoint — choose the smaller workable shape)
  • request/response contract for "wrapper posted something; BotShield either accepted it and minted _bs_verified, or declined"
  • cache/versioning/CSP/docs story for the wrapper itself

Gate:

  • page with the script tag loads cleanly
  • page without the tag behaves exactly like today
  • no output filter / HTML rewriting introduced
  • missing wrapper / blocked script never breaks the page; it only means the client stays unverified

E17.2 — first provider-backed adapter

Do one token-based invisible/background provider first, using the existing M8 verification path. Turnstile is the likely first choice because it is already supported, already in the provider registry, and has non-interactive / invisible modes.

Scope:

  • wrapper loads provider asset
  • provider returns a token in background flow
  • wrapper POSTs token to BotShield
  • BotShield reuses the existing provider row + siteverify shim
  • BotShield issues _bs_verified

Gate:

  • real page loads immediately
  • background verification completes
  • next request is cookie-valid DECLINED
  • misconfigured provider config fails closed into "not verified yet," not a silent trust grant

Only after this works do we harden the public E17 directive and bootstrap surface.

E17.3 — second provider class

Add one materially different provider shape to test whether the wrapper abstraction is actually real:

  • score-based (recaptcha-v3) and/or
  • passive/invisible widget with different client semantics

Why this step exists:

  • token-based invisible widgets are one class of problem
  • score-returning providers are another
  • if the same wrapper contract cannot hide both cleanly, we learn that early and keep the adapter layer honest

Gate:

  • BotShield can consume either a token result or a provider score without cloning the whole provider stack
  • operator docs still describe one BotShield integration, even if adapter caveats differ underneath

E17.4 — additional provider adapters

Only then add more providers one by one:

  • hCaptcha
  • Friendly
  • GeeTest
  • Cap-like/self-hosted external challenge services

Each adapter is a separate "prove it works" landing. E17 should not promise support for all existing M8 providers on day one.

E17.5 — native BotShield built-in mode

Once the wrapper/verify shape is proven with external providers, add a simple native adapter so BotShield has an in-tree option that does not require a third-party client runtime.

Start small:

  • background PoW or another low-maintenance proof
  • no elaborate DOM fingerprinting
  • same wrapper POST contract as the provider adapters

This lets BotShield grow a built-in embedded mode over time without making E17's first release depend on a browser-fingerprinting project.

E17.6 — optional advanced native probe

The original embedded-browser-probe idea is not dead, but it is explicitly not v1.

Only attempt it if:

  • E17.1–E17.5 prove that the embedded wrapper model is useful in the real world, and
  • the simple native mode is not enough, and
  • we are willing to own the privacy/documentation/maintenance cost of an ongoing browser-probe arms race

That becomes a separate go/no-go decision, not an assumed part of initial E17.

Gate

  • BotShieldSilentMode interstitial remains the default and disables all E17 endpoints.
  • With E17 enabled and the wrapper tag present, a supported provider can verify in the background and produce _bs_verified without a splash page.
  • With E17 enabled but the wrapper missing, blocked by CSP, or not yet supported for the configured provider, the site still works and M7 remains the fallback path for future silent-tier requests.
  • Provider-backed E17 reuses the existing M8 verification config on the same scope by default.
  • Native E17 mode, when added later, uses the same wrapper contract and the same BotShield trust cookie issuance.

Risks

  • Provider heterogeneity. "Invisible" does not mean the same thing across providers. Some may still present UI. E17 must hide integration complexity, not fake uniform behavior.
  • Config drift. Duplicating interstitial and embedded provider config would create a maintenance trap. Reuse by default.
  • CSP / asset loading / versioning. Wrapper JS is ours, but some adapters load third-party assets. Document required script-src allowances and offer asset-URL overrides where needed.
  • Operational uncertainty. We do not yet know which providers really fit this shape cleanly. That's why the plan is phased and provider-by-provider.
  • Native scope creep. A full browser-probe system is tempting and expensive. Keep it explicitly out of early E17.

Position relative to M7: E17 ships after M7 is real and exercised, because M7 is the fallback when the wrapper is absent, blocked, or the configured adapter has not been proven yet.

Position relative to M8: E17 should stand on M8's shoulders. Provider verification, secrets, expected-hostname/action checks, and timeouts belong to the existing M8 layer unless a concrete adapter proves otherwise.

Position relative to E5: independent but complementary. E5 is app → module reputation feedback; E17 is module/wrapper → provider/native → module verification. The app can stay extremely simple in E17: include one BotShield script tag and let BotShield own the rest.

E18 — Inline form captcha (verify-on-submit) (shipped)

Today BotShield handles two captcha territories — page-level interstitial (M7/M8) and page-level embedded (E17). It does not handle the third classic captcha territory: a captcha widget embedded inline in a form, validated when the form is submitted.

Operators with a contact form, signup flow, or comment box currently have to set up Turnstile / hCaptcha / reCAPTCHA separately even when BotShield is already configured for the same provider on the same vhost. They duplicate sitekey/secret config in two places, and their app handler has its own siteverify integration. E18 removes that duplication.

Core idea:

  1. Operator already has BotShieldCaptchaProvider / BotShieldCaptchaSiteKey / BotShieldCaptchaSecretFile set on the vhost (or scope) for M8 interstitial use.
  2. Operator adds BotShieldFormCaptcha on to the form-submit URL, plus one HTML attribute on the form's captcha-widget slot.
  3. BotShield emits the right per-provider widget markup inline (reusing the E17 wrapper foundation for the rendering shell).
  4. On form POST, BotShield runs request-time, parses the body, extracts the provider-specific captcha-response field, calls siteverify (reusing the existing M8 path), and either lets the request through (DECLINED — app handler runs) or rejects it.
  5. On successful verify, BotShield ALSO mints _bs_verified so future BotShield friction on this client is skipped. Free side effect; operator gets it without setup.

This is a fundamentally different shape from M7/M8/E17:

  • M7/M8 are page-level guards: "prove you're human before you see this page." Friction is invisible (M7) or front-and-center (M8 interstitial).
  • E17 is page-level silent: "verification happens in background, page loads normally."
  • E18 is form-level with operator-chosen friction: "captcha sits inside a form the user is already filling out; submit-time validation is part of the form's already-mandatory roundtrip." The user's affirmative "I'm not a bot" interaction is the point — there's no UX hiding to do.

Reusable infrastructure

Most of E18 is rewiring already-shipped code, not new:

  • provider registry, siteverify HTTP client, expected-hostname checks, timeouts, in-flight cap — all already in M8
  • BotShieldCaptcha* directives — reused as-is, no new per-form provider config
  • HMAC, secrets-file management, mode-600 hygiene — reused
  • _bs_verified cookie issuance — reused (form-submit success mints the same cookie M8 mints)
  • decision log, metrics, reason chain — reused

What's genuinely new:

  • Widget rendering shell. Reuses the E17 embedded.js pattern but emits provider-specific widget markup at the data-bs-form-captcha slot instead of running a Worker.
  • Request-body inspection — load-bearing new code (see Risks below).
  • BotShieldFormCaptcha on directive — opt-in per scope.

Candidate directive surface

# Existing provider config — reused as-is.
<Location /contact>
    BotShieldCaptchaProvider   turnstile
    BotShieldCaptchaSiteKey    1x00000000000000000000AA
    BotShieldCaptchaSecretFile /etc/botshield/turnstile-secret
</Location>

# NEW — opt this URL into form-tier verification.
<Location /contact/submit>
    BotShieldFormCaptcha on
    # Optional: where to send the user on a bad captcha.
    # Default: 403 with a tiny error page.
    # BotShieldFormCaptchaFailRedirect /contact?bad-captcha=1
</Location>

Operator's HTML:

<form action="/contact/submit" method="POST">
  <input name="email" type="email">
  <textarea name="message"></textarea>
  <div data-bs-form-captcha></div>     <!-- BotShield injects widget here -->
  <button>Send</button>
</form>
<script src="/botshield/form-widget.js" defer></script>

The form-widget.js fetches the configured provider for the current scope (same /botshield/embedded-bootstrap-style endpoint as E17, shared infrastructure), injects the right widget markup at the data-bs-form-captcha slot, done.

Submit-time flow

  1. Browser POSTs email, message, and the provider-specific captcha token field (cf-turnstile-response, h-captcha-response, g-recaptcha-response, etc.) to /contact/submit.
  2. BotShield's request handler runs (BotShieldFormCaptcha on active for this scope). Reads the request body.
  3. Provider registry tells BotShield the field name to look for.
  4. BotShield calls siteverify via the existing M8 path.
  5. Token good → BotShield mints _bs_verified (so the next request from this client is DECLINED through), then returns DECLINED — app's submit handler runs as if BotShield wasn't there.
  6. Token bad / missing → BotShield returns 403 (or operator- configured fail-redirect). App's submit handler never runs.

Position relative to E17

E18 builds on the E17 wrapper foundation. Specifically:

  • /botshield/embedded.js and /botshield/embedded-bootstrap are reused to deliver the widget shell + provider config to the client.
  • BotShieldSilentMode embedded and BotShieldFormCaptcha on are orthogonal directives — a scope can have either, both, or neither.
  • If E17 PoC fails the timing model and we kill embedded silent verification, E18 can still ship: the wrapper foundation remains useful as a captcha-widget loader even if the silent-verify background flow doesn't pan out.

Phasing

E18.1 — request-body inspection foundation:

  • input filter (or request-time body buffering) for application/x-www-form-urlencoded — covers the 80% case
  • field extraction by provider-known name
  • siteverify call + decision
  • 403 or fail-redirect on bad token
  • _bs_verified minting on good token

Gate:

  • happy path: real form, real captcha solve, app handler sees clean request
  • bad-token path: 403 returned, app never sees the request
  • missing-token path: 403 returned with diagnostic
  • body-size cap: oversize body rejected before siteverify call

E18.2 — JSON body shape:

  • application/json (modern AJAX form submits) — needs JSON parser (json-c is already linked for E5 / E8.2)

E18.3 — widget rendering shell:

  • data-bs-form-captcha HTML attribute recognized by form-widget.js
  • per-provider markup emission (Turnstile <div class="cf-turnstile" data-sitekey="...">; hCaptcha <div class="h-captcha" data-sitekey="...">; etc.)
  • provider-script lazy-load (Cloudflare's challenge platform script, hCaptcha's, etc.) with the same caching/CSP discipline as E17

Gate:

  • one configured provider renders correctly inline in a real form
  • second provider does too without per-provider code paths in the client wrapper

Risks

  • Body inspection is genuinely new for this module. Today mod_botshield touches request lines, headers, and cookies — never the body. Reading the body means an input filter or a request- time ap_setup_client_block / ap_get_client_block loop, plus a body-size cap so an attacker can't exhaust memory. Has to play nicely with whatever body parsing the app's handler does — read once, buffer, replay.
  • JSON form submits. Modern SPA form-handling often POSTs JSON rather than form-encoded. Same shape; E18.2 adds it on top of the URL-encoded foundation.
  • Multipart / file-upload forms are out of scope. Forms with multipart/form-data (file attachments) need a streaming parser
    • temp-file buckets and aren't a fit for BotShield's design. Operators with file-upload forms put the captcha on a separate non-upload form.
  • App-handler interactions. Some apps re-read the body via their own filter chain. BotShield must consume + buffer + replay the body so downstream handlers see the same bytes. The Apache filter API has well-trodden patterns for this; just have to follow them carefully.
  • Security review territory. Touching request bodies is the shape that historically leads to bypass bugs (CRLF injection, NUL truncation, encoding mismatches). E18.1 needs ASan/UBSan fuzz coverage on the body parser.

As shipped — v1 covers the URL-encoded happy path and reuses the M8 siteverify infrastructure exactly. The architectural piece worth flagging is the body-replay model:

  • Fixup hook reads the entire body via ap_get_brigade against the request's input filter chain into a 256 KB pool-allocated buffer
  • After siteverify decides, the hook adds a one-shot input filter (BS_FORM_REPLAY) at the top of r->input_filters that emits the buffered body + EOS when the downstream handler asks for it
  • ap_add_input_filter_handle puts our filter ahead of the (now drained) protocol filters, so the handler's first read hits the buffered copy. The framework slices buckets to honor the handler's readbytes request so emit-the-whole-body in one bucket is correct in practice
  • Filter self-removes via ap_remove_input_filter after first emission so subsequent reads see only EOS

Deliverables (shipped):

  • BotShieldFormCaptcha on directive (per-scope, opt-in)
  • Fixup hook reads + validates + decides
  • BS_FORM_REPLAY input filter for body replay
  • Reuses M8 siteverify, hostname binding, action binding, v3 score threshold — security-review #1 parity
  • 256 KB body cap (BS_FORM_CAPTCHA_BODY_MAX); oversize → 413
  • Wrong content-type (multipart and other shapes) → 415 with diagnostic so operators notice the gap
  • Missing scope provider config → 503 fail-loud (not silent allow)
  • Bad token / hostname mismatch / action mismatch / v3 score below threshold → 403, app handler never runs
  • Successful verify → mints _bs_verified (passes_captcha=1) so future BotShield friction skips this client
  • pytest coverage in tests/pytests/test_form_captcha.py covering missing token / empty token / wrong content-type / valid Turnstile round-trip via Cloudflare always-pass keys / misconfigured scope / JSON variants of the above

Follow-ups since v1:

  • E18.3 (shipped): application/json body support — fixup hook branches on Content-Type, json-c parses, same token field name as the URL-encoded path. Same siteverify, same body replay.
  • E18.4 (shipped): form-widget shell — /botshield/form-widget.js detects [data-bs-form-captcha] slots, reads data-bs-provider + data-bs-sitekey, injects per-provider markup (cf-turnstile, h-captcha, g-recaptcha, frc-captcha) and lazy-loads the provider's CDN script. Operators don't have to remember per-provider class names; the wrapper abstracts them.

Out of scope:

  • multipart/form-data (file uploads in the same form). Streaming multipart parsing with temp-file buckets isn't a fit for BotShield's design. Operators with file-upload forms put the captcha on a separate non-upload form or pre-screen with silent-tier embedded verification (E17).

Why this fits BotShield's product

The current value prop is "front-door defense." E18 expands it to "BotShield owns all your captcha needs" — which is a real operational simplification for any site that has both perimeter challenges AND inline-form captchas. Provider config lives in one place; secrets in one place; siteverify in one place; rotation (E16) covers it all uniformly.
